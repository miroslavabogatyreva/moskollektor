# Счётные скрипты по выгрузке

Здесь лежит то, чем получены числа в `docs/day-one.md` и `docs/for-ml-team.md`.
Скрипты сохранены 15.09.2026 из временного каталога, где их писали, — **именно затем,
чтобы числа можно было пересчитать**. В тот же день мы потеряли полдня на споре
о числе отказов (11 454 против 10 416) ровно потому, что первый счёт делался на лету
и скрипта после себя не оставил. Второй оставил, и этим спор закончился.

## Что нужно, чтобы запустить

DuckDB в отдельном окружении, в системный Python ничего ставить не надо:

```
python3 -m venv ~/.venv/mk && ~/.venv/mk/bin/pip install duckdb
```

Скрипты работают **из каталога с промежуточными Parquet**, а не из репозитория:
пути к `parquet/j*.parquet`, `episodes_all.parquet` и прочим написаны относительными.
Заведите рабочий каталог вне репозитория (3,3 ГБ Parquet в git не нужны), скопируйте
туда скрипты и запускайте оттуда.

## Порядок запуска

| Шаг | Команда | Сколько идёт | Что появляется |
|---|---|---|---|
| 1 | `python to_parquet.py` | 35 с | `parquet/j2019…j2026.parquet` — восемь csv переведены в Parquet, 3,3 ГБ, 313 546 016 строк, отбраковано 0 |
| 2 | `python episodes.py 8` | ~3 мин | `episodes_all.parquet` — 1 499 290 эпизодов `Неисправен` с `t_start`, `t_end`, `dur_h`, `close_val`. Аргумент — на сколько частей резать каналы, чтобы влезть в память |
| 3 | `python z3_features.py` | ~1 мин | `chanday.parquet` — календарь «канал-день», 1 015 557 канало-дней с записями |

Дальше любой из счётных скриптов, они независимы:

| Скрипт | Что считает | Где лежит результат |
|---|---|---|
| `clusters.py` | пачки отказов: 587 эпизодов проверочного окна складываются в 166 инцидентов | `docs/day-one.md` п. 1, `docs/acceptance-test.md` М-18 |
| `z2.py`, `z2b.py` | связь префикса с объектом: даты рождения площадок, состав подсистем, совместные срабатывания | `docs/for-ml-team.md` разд. 6 и 7 |
| `z3_rules.py` | одиннадцать правил предсказания: полнота, точность, упреждение | `docs/for-ml-team.md` разд. 10, таблица правил |
| `z3_ceiling.py` | потолок полноты при оракуле — 0,59 по парку, 0,40 по дыму | там же, абзац «почему это потолок» |

`z3_rules.py` и `z3_ceiling.py` подключают `code/predictive_metrics.py` — методика
замера у них та же, что на приёмке, иначе числа не сравнились бы.

## Две вещи, которые в скриптах сделаны нарочно

**Сортировка по паре `(ts, ev)`** — по времени и номеру события, а не по порядку строк
в файле. Файлы заказчика по времени не отсортированы: в журнале за 2026 год время идёт
назад между соседними строками 741 744 раза. Поменяете сортировку — получите другое
число отказов, и расхождение будет около 9 %.

**Резка каналов на части по `ch % K`** в `episodes.py`. Оконная функция по всем
313 млн строк не влезает в память ноутбука; резка по остатку от деления даёт полные
истории каналов в каждой части, поэтому эпизоды не рвутся на границе. Увеличьте `K`,
если не хватает памяти, — на результат это не влияет.
