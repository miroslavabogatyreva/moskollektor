# Как поднять стенд

Полная инструкция по развёртыванию на сервере заказчика — `docs/install.md`
(сервер, сеть, Docker, доступ к базе, резервные копии). Как собрать образы —
`docs/build.md`. Здесь только то, что нужно, чтобы стенд заработал на своей машине.

Проверено 15.09.2026 с нуля дважды. Второй прогон — после того, как nginx научили
адресам нового вида, а `check-tls.sh` — четвёртому вердикту: стенд снесли вместе
с томами, удалили `.env` и `nginx/certs`, прошли три шага ниже и получили оба
контейнера `healthy` за 12 секунд. Каждая команда из этого файла прогнана и отвечает
тем, что здесь написано, — включая оба протокола замера TLS.

## Что должно стоять на машине

Docker с плагином `compose` — тем, который пишется через пробел, а не старый
`docker-compose` через дефис: файл `docker-compose.yml` написан под плагин.
Проверить:

```
docker --version          # у нас работало на 29.6.2 и 29.8.0
docker compose version    # у нас 5.3.1 на маке и 5.5.1 на сервере
docker info               # демон должен отвечать, а не ругаться на сокет
```

На маке с Apple Silicon перед этим надо запустить Docker Desktop, иначе `docker info`
напишет `connect: no such file or directory` и ничего не поднимется.

## Три шага, все обязательные

Выполнять из каталога `deploy`.

**1. Завести файл переменных.** В git его нет, у нового человека его не будет.

```
cp .env.example .env
```

Дальше открыть `.env` и заменить `POSTGRES_PASSWORD=СМЕНИ-МЕНЯ` на настоящий пароль.
Пропустить этот шаг нельзя: без `.env` compose подставит пустые строки, база откажется
разворачиваться и напишет в журнал `You must specify POSTGRES_PASSWORD to a non-empty
value for the superuser`.

**2. Выпустить самоподписанный сертификат.** Его в git тоже нет.

```
sh make-cert.sh
```

Скрипт кладёт `server.crt` и `server.key` в `nginx/certs`. Пропустить нельзя: nginx
не стартует и напишет `cannot load certificate "/etc/nginx/certs/server.crt"`.

**3. Поднять стенд.**

```
docker compose up -d
```

**Если запустили не в том порядке.** `docker compose up -d` без шагов 1 и 2 поднимет
контейнеры, и они тут же упадут: база — на пустом пароле, nginx — на отсутствующем
сертификате. Каталог `nginx/certs` при этом появится пустым, его создаёт докер сам под
точку подключения — не принимайте это за сделанный шаг 2. Выход: `docker compose down`,
потом шаги 1 и 2, потом `up -d` заново.

## Убедиться, что поднялось

**Команда `docker compose up -d` возвращает 0, даже когда обе службы падают сразу
после старта.** Она сообщает, что контейнеры созданы и запущены, а не что процессы
внутри них работают. Поэтому проверять надо отдельно:

```
docker compose ps
```

Оба контейнера должны дойти до `(healthy)`: база примерно за 20 секунд, nginx
примерно за 15. Пока стоит `(health: starting)` — ещё рано делать выводы.

Дальше проверить, что сервер отвечает:

```
curl -sk -o /dev/null -w '%{http_code} %{http_version}\n' https://127.0.0.1/   # ждём: 200 2
curl -sk -o /dev/null -w '%{http_code} %{http_version}\n' 'https://[::1]/'     # ждём: 200 2
curl -s  -o /dev/null -w '%{http_code}\n' http://127.0.0.1/                    # ждём: 301
curl -s  -o /dev/null -w '%{http_code}\n' 'http://[::1]/'                      # ждём: 301
```

Адреса здесь написаны цифрами нарочно. Имя `localhost` на этой машине разворачивается
в два адреса, и какой из них возьмёт программа — зависит от программы: `curl` сегодня
уходит в `::1`. Проверив по имени, вы проверите один вход из двух и не будете знать,
какой. Квадратные скобки вокруг `::1` обязательны, иначе `curl` примет двоеточие
внутри адреса за отделитель порта.

Сертификат самоподписанный, поэтому `curl` без `-k` откажется с ним работать — это
ожидаемо, а не поломка.

База отдельной командой, пароль для неё не нужен:

```
docker compose exec -T db pg_isready
# ждём: /var/run/postgresql:5432 - accepting connections
```

**Зайти в базу запросом.** Имя пользователя и имя базы — не `postgres` и не `mos`: они
задаются в `.env` переменными `POSTGRES_USER` и `POSTGRES_DB`, и в `.env.example` там
стоит `moskollektor`. Скопировав команду с другим именем, вы получите
`role "mos" does not exist` при полностью исправной базе:

```
docker compose exec -T db psql -U moskollektor -d moskollektor -c '\dn'
# ждём: 12 строк. Наших девять — asset feat geo load maint permit pred ref smvu;
# ещё три служебные: public, а также tiger и topology, их заводит PostGIS
```

**Накатить схему** (MOS-85, 15.09.2026):

```
docker compose --profile app build migrate
docker compose --profile app run --rm migrate
```

Берёт `db/migrations/*.sql` по возрастанию номера, каждый файл в своей транзакции,
список накатанного — в `public.schema_migration`. Повторный прогон ничего не
накатывает заново и выходит с кодом 0 — так и проверять, что накат прошёл
целиком: `docker compose --profile app run --rm migrate` второй раз подряд.
Сиды из `db/seed/*.sql` тот же контейнер накатывает после миграций — порядок
и ручной обход описаны в конце раздела.

**Проверять так можно только после заливки справочников, и вот почему.** Миграция
`029_ml_readonly.sql` заводит представление `smvu.channel_collector` и самопроверкой
считает по нему коллекторы: их должно быть 16. На пустой базе справочника ещё нет,
считать нечего, и до 22.09.2026 накат на этом вставал — доезжал до `028` и возвращал
код 1, а `api` и `worker` не поднимались вовсе, они ждут `migrate` через
`condition: service_completed_successfully`. Теперь пустой справочник три проверки
пропускает и говорит об этом строкой `029: справочник каналов пуст — три проверки
пропущены`, а накат идёт до конца: на чистой базе «готово: 27 новых, 0 уже были».

Порядок установки от этого не меняется и остаётся прежним: накатить схему, залить
выгрузку (раздел ниже), потом повторить `--channels` — он дозаполнит `collector`
и `location_kind` уже залитым каналам (`backend/app/ingest/channel_place.py`).

Каждый проход с `--channels`, и первый, и повторный, заодно рисует синтетическую
геометрию: оси 16 коллекторов и отрезки 3 173 участков в `geo.geo_object`, ссылку
`ref.object_xref.geo_object_id` (`backend/app/ingest/synthetic_geometry.py`, MOS-45).
Отдельного шага нет, и повтор ничего не удваивает. В журнале заливки строка
`геометрия: коллекторов 16, частей 32, участков 3173`; без миграции 046 или без
`--objects` она говорит «пропускаю» и называет причину.

**На уже работающем стенде**, где справочник залит раньше, чем появилась миграция 046,
перезаливать ничего не нужно. После пересборки образов и наката `migrate` геометрию
рисует отдельная команда:

```
docker compose exec -T api sh -c 'python -m app.ingest.synthetic_geometry --dsn "$DATABASE_URL"'
```

Она работает одной транзакцией и печатает `геометрия: коллекторов 16, частей 32,
участков 3173`, а затем время. На стенде 23.09.2026 весь проход занял 0,4 с (замер
в транзакции с откатом). Без аргументов та же команда запускает только самопроверку.

Файл миграции через `psql -f` руками не гонять: результат не попадёт в журнал,
и следующий настоящий прогон попробует накатить его ещё раз и упадёт на
`already exists`. На стенде, где часть файлов уже накатана руками (наш случай
15.09.2026 до появления `migrate.py`), это обходится один раз через
`deploy/bootstrap-schema-migration.sql` — второй раз этот сценарий заводить
незачем.

**Сиды накатывает тот же контейнер `migrate`, сразу после миграций.** Берёт
`db/seed/*.sql` по имени файла, каждый файл в своей транзакции, как миграции.
Сиды идемпотентные: вставки написаны `INSERT … ON CONFLICT`, поэтому повторный
прогон применяет их заново и не удваивает строки. Руками накатывать
сиды больше не нужно. Раньше накат сидами не занимался, и 18.09.2026 на стенде
это выстрелило: права в `ref.role_permission` отстали от git, и admin получал
ответ 403 (доступ запрещён) на запрос `GET /api/settings`, пока `db/seed/rbac.sql`
не накатали руками.

**Исключение одно.** Вставка учётных записей в `db/seed/rbac.sql` идёт в
`ref.app_user` с `ON CONFLICT (login) DO UPDATE` по одной колонке `full_name`:
`password_hash` и `auth_source` у существующего логина она не трогает. Первый
вход через каталог LDAP ставит `auth_source='ldap'` и `password_hash=NULL`
(`backend/app/api/auth.py:142`), и повторный накат сида с перезаписью этих
колонок вернул бы ldap-пользователю `auth_source='local'` и демо-хеш argon2 —
то есть снял бы вход по каталогу и подменил пароль. Колонку `is_active` сид тоже
не трогает: блокировка пользователя из интерфейса (MOS-226) обязана переживать
перезаливку.

**Ручной обход — когда накатывать надо один файл, а не порядок установки.**
Например, вы поправили справочник в `db/seed/setpoints.sql` и не хотите гонять
весь `migrate`:

```
docker compose exec -T db psql -U moskollektor -d moskollektor -f /dev/stdin < ../db/seed/<файл>.sql
```

## Залить выгрузку СМВУ

Заливает `backend/app/ingest/smvu_csv.py`, командой из корня репозитория (не из `deploy`).
Порядок внутри команды обязателен: объекты, каналы, журнал — его держат внешние ключи.

```
PYTHONPATH=backend .venv/bin/python -u -m app.ingest.smvu_csv \
    --dsn "postgresql://moskollektor:ПАРОЛЬ@127.0.0.1:5432/moskollektor" \
    --objects dataset/справочник_объектов_диспетчер.csv \
    --channels dataset/справочник_каналов_датчиков.csv \
    dataset/ext-journal-*.csv
```

Пароль берётся из `deploy/.env`, переменная `POSTGRES_PASSWORD`. Нужен `asyncpg`:
`python3 -m venv .venv && .venv/bin/pip install asyncpg`.

**Команду можно запускать повторно.** Уже залитые справочники она пропускает
с сообщением, а не падает на существующем ключе. Журнал повторный прогон зальёт
заново — перед ним `TRUNCATE smvu.reading`.

**Где заливать.** На сервере, а не на своей машине: база вырастает до 55 ГБ,
и на маке разработчика это кончается нехваткой места на седьмом файле из восьми
(проверено 15.09.2026, разбор — `docs/server.md`). На сервере выгрузка уже лежит
в `/srv/moskollektor-hakaton-data/dataset`, по сети не гоняется ничего.

**В три потока вместо одного.** Годовые файлы ложатся в разные месячные партиции
и друг другу не мешают, поэтому их можно лить параллельно: `--slot` даёт каждому
процессу свою промежуточную таблицу. Замер 15.09.2026: один поток 25 тыс. строк/с,
три потока 83 тыс. Разложить можно так:

```
run_slot() { slot=$1; shift; nohup env PYTHONPATH=backend .venv/bin/python -u \
  -m app.ingest.smvu_csv --dsn "$DSN" --slot "$slot" --keep-indexes "$@" \
  > load-$slot.log 2>&1 & }
run_slot 1 $D/ext-journal-2019.csv $D/ext-journal-2020.csv $D/ext-journal-2021.csv
run_slot 2 $D/ext-journal-2022.csv $D/ext-journal-2023.csv $D/ext-journal-2026.csv
run_slot 3 $D/ext-journal-2024.csv $D/ext-journal-2025.csv
```

Имена переменных только латиницей: в `bash` на сервере `СЛОТ=1` отвечает
`command not found`, подстановка даёт пустоту, и процесс запускается не с теми
параметрами — молча.

**Чего ждать.** 313 546 016 строк идут около часа в три потока и три с лишним
в один. Загрузчик печатает после каждого файла размер базы и остаток свободного
места — нехватка обязана вылезти на третьем файле, а не на восьмом.

**Вторичные индексы на время заливки снимаются.** В несколько потоков их строит
отдельная команда, когда все потоки закончили, — иначе потоки взялись бы строить
их наперегонки:

```
PYTHONPATH=backend .venv/bin/python -m app.ingest.smvu_csv --dsn "$DSN" --build-indexes
```

Замер 15.09.2026 на 313 млн строк: по каналу 4,0 мин, по участку 4,1 мин,
по тревогам 1,1 мин. Что они дают, видно на одном запросе «показания участка
за март 2025»: без индекса 833 мс, с индексом 1,3 мс.

**Сверить залитое:**

```
PYTHONPATH=backend .venv/bin/python -m app.ingest.smvu_csv --dsn "$DSN" --check
```

Девять контрольных чисел разом: строки, каналы, заглушки, участки, объекты, пустота
партиции `default`, расхождения денормализации, месяцы без данных. 15.09.2026
расхождений ноль.

Проверить, что получилось:

```
docker compose exec -T db psql -U moskollektor -d moskollektor -c "
SELECT count(*) FROM smvu.reading;
SELECT count(*) AS в_default FROM smvu.reading_default;          -- обязано быть 0
SELECT * FROM load.batch ORDER BY id DESC LIMIT 1;               -- отчёт о качестве
SELECT rule_code, message, payload FROM load.error ORDER BY id;  -- причины отказа
"
```

## Поднять заглушку модели

Пока обученной модели нет, её место занимает `ml-stub/` (MOS-66). Собирается из корня
репозитория, потому что в образ едет и `contracts/`:

```
docker build -t moskollektor/ml-stub:latest -f ml-stub/Dockerfile .
docker compose --profile app up -d ml

Проверить:

```
docker compose exec -T ml python -c "import urllib.request,json; print(json.load(urllib.request.urlopen('http://ml:8100/model')))"
# ждём: model_version stub-0.1, feature_schema feat.v1, degraded True

## Поднять каталог LDAP (демо, НФ-76, MOS-39)

Заказчик каталога не даёт («любой LDAP сервис» — ответ 31, `docs/meetings/2026-09-17-эксперты.md`),
поэтому НФ-76 доказываем своим маленьким сервером. Профиль отдельный от `app`, поднимается
вторым флагом:

```
docker compose --profile app --profile ldap up -d
```

Проверить: любая из четырёх демо-учёток биндится, пароль у всех `LdapDemo#1`.

```
docker compose exec -T ldap ldapwhoami -x \
  -D "uid=ldap_tech1,ou=people,dc=moskollektor,dc=local" -w 'LdapDemo#1' -H ldap://127.0.0.1
# ждём: dn:uid=ldap_tech1,ou=people,dc=moskollektor,dc=local
```

**Заблокировать и вернуть учётку** — `deploy/ldap/block-user.sh`, отдельная команда,
не трогает пароль (уводит DN в сторону, `ldapmodrdn`):

```
sh deploy/ldap/block-user.sh ldap_tech1          # bind после этого — Invalid credentials (49)
sh deploy/ldap/block-user.sh --undo ldap_tech1   # bind снова проходит
```

**Подключить настоящий AD/LDAP заказчика вместо демо-каталога** — три переменные
в `.env`, ни одной правки кода:

```
LDAP_URI=ldap://<их контроллер>:389
LDAP_BASE_DN=<их base DN>
LDAP_USER_TEMPLATE=uid={login},<их шаблон DN>   # {login} — обязательный плейсхолдер
```

Профиль `ldap` в `docker compose --profile app up -d` при этом просто не поднимать —
контейнер demo-каталога и настоящий AD не должны стоять рядом одновременно.

**Гасить только поимённо.** `docker compose down` без имени сервиса убирает ВСЕ
контейнеры проекта, а не только профиль `ldap` — если рядом работает `db`/`nginx`
(в том числе из другого worktree на этой же машине), они уедут тоже. Верно:
`docker compose stop ldap && docker compose rm -f ldap`.

## Поднять API и выложить интерфейс

**Найдено 16.09.2026: из шести контейнеров HLD на стенде работали три.** Контейнер `api`
не поднимался ни разу, а на корне nginx отдавал заглушку «Москоллектор — стенд»,
написанную в первый день. По кодам ответа строка приёмки М-03 «интерфейс открывается
в браузере по ссылке» выглядела закрытой — а открылась бы эта заглушка.

**Сначала код на сервер.** На сервере лежит rsync-копия рабочего дерева, и она отстаёт.
Каталог `deploy/.env` не трогать: там пароль базы, и однажды он уже приехал туда копией
с мака (разбор — `docs/server.md`).

```
rsync -a --delete --exclude '__pycache__' backend/app/ root@СЕРВЕР:/srv/moskollektor/backend/app/
rsync -a backend/Dockerfile backend/requirements.txt root@СЕРВЕР:/srv/moskollektor/backend/
rsync -a db/migrations/ root@СЕРВЕР:/srv/moskollektor/db/migrations/
rsync -a db/seed/ root@СЕРВЕР:/srv/moskollektor/db/seed/
rsync -a contracts/ root@СЕРВЕР:/srv/moskollektor/contracts/
rsync -a deploy/docker-compose.yml root@СЕРВЕР:/srv/moskollektor/deploy/
```

**Каталог `db/seed/` нужен на сервере ради сборки образа.** `backend/Dockerfile`
вшивает сиды строкой `COPY db/seed ./db/seed` рядом с `COPY db/migrations
./db/migrations`, контекст сборки — корень репозитория на сервере, и без каталога
`db/seed/` сборка упадёт.

**Потом образ и контейнер.** `migrate` поднимется сам: `api` ждёт его через
`condition: service_completed_successfully`, миграции накатываются по журналу
и повторно ничего не делают, а сиды применяются заново каждый раз — это их
устройство, а не ошибка.

```
cd /srv/moskollektor
docker compose -f deploy/docker-compose.yml --profile app build api
docker compose -f deploy/docker-compose.yml --profile app up -d api
```

**Интерфейс — это статика, а не контейнер.** nginx монтирует `./nginx/html`
на `/usr/share/nginx/html`, поэтому собранный фронт кладётся туда файлами:

```
cd frontend && npm run build          # проверить бюджет: gzip -c dist/assets/*.js | wc -c < 153600
rsync -a --delete frontend/dist/ root@СЕРВЕР:/srv/moskollektor/deploy/nginx/html/
```

**Важно про порядок.** Каждая правка фронта требует повторить оба шага, иначе стенд
покажет вчерашнюю версию, а комиссия — вчерашний интерфейс. На нашем стенде оба шага
с 27.09.2026 делает `deploy/deploy.sh` после каждого пуша в master — `docs/server.md`.

**Проверять уловом, а не статусом.** `docker compose ps` скажет `running` и у контейнера,
который отвечает пятисотками. Замер 16.09.2026, все ответы с боевого контура:

```
curl -sk -o /dev/null -w "%{http_code}\n" https://СЕРВЕР/                      # 200, index.html интерфейса
curl -sk -o /dev/null -w "%{http_code}\n" https://СЕРВЕР/dashboard             # 200 — try_files отдаёт index.html
curl -sk -o /dev/null -w "%{http_code}\n" https://СЕРВЕР/api/risks             # 401 без заголовка
curl -sk -H "X-User-Login: dispatcher1" -o /dev/null -w "%{http_code} %{size_download}\n" \
     https://СЕРВЕР/api/risks                                                   # 200, 455 865 байт
```

Последняя строка — главная: она доказывает, что интерфейс и данные приходят с одного
адреса, без туннелей. Размер ответа — это 3 173 участка с уровнем риска.

**Ловушка, на которую я наступил дважды за день.** В `bash` на сервере не работают
кириллические имена переменных: `for п in …` отвечает `not a valid identifier`, цикл
не выполняется вовсе, а вывод выглядит как пустой результат, а не как ошибка. В командах
для сервера имена только латиницей — это записано и в `docs/server.md`, и я всё равно
наступил.

## Замер TLS для приёмки

Строку НФ-75 закрывает отдельный скрипт, его вывод и есть протокол:

```
sh check-tls.sh 127.0.0.1 > ../docs/protocol-tls-ipv4.md
sh check-tls.sh ::1       > ../docs/protocol-tls-ipv6.md
```

Протокола два, и оба обязательны: nginx слушает оба вида адресов, а закрыт правильно
может оказаться только один — по одному файлу этого не увидеть. В один файл писать
нельзя, второй прогон затрёт первый.

Нужен `nmap`: на маке `brew install nmap`, на сервере `apt-get install nmap`.
Что должно получиться: секции TLSv1.2 и TLSv1.3 с тремя наборами в каждой, секций TLSv1.0 и TLSv1.1 нет вообще, а у форсированных
подключений `-tls1` и `-tls1_1` в строке «Итог» стоит «СЕРВЕР ОТКЛОНИЛ».

## Снести стенд

```
docker compose down       # убирает контейнеры, данные базы остаются в томе
docker compose down -v    # убирает и тома, база стирается насовсем
```

Данные переживают и `restart`, и `down` без `-v` — проверено 15.09.2026 на таблице
из трёх строк: после пересоздания контейнера строки остались с прежними метками времени.
