# Дашборд рисков ОДС: что на экране, почему так и как считается

Документ описывает макет `dashboard-mockup.html`. Для каждого блока написано,
зачем он там, из каких данных берётся число и какой формулой считается.
В конце — список того, что надо получить от АО «Москоллектор», и что в макете
изменится, когда данные придут.

**Важно про числа.** Все значения в макете вымышленные. Настоящие в нём только
коды типов датчиков (ДМТ-6, МОД, ГАСБ, ТК-1, СЕНСИС-500), нормативные пороги
и структура кода объекта. Ни одно число не надо показывать заказчику как факт.

Имена таблиц и полей ниже — из наших миграций в `db/migrations/`:
`db/migrations/004_events.sql` (события СМВУ, признаки, прогнозы), `db/migrations/001_assets.sql`
(реестр оборудования), `db/migrations/003_permits.sql` (наряды-допуски), `db/migrations/002_geo.sql`
(геометрия и риск объектов).

Сетка взята из чек-листа компоновки Колоколова и Зыкиной — один экран без
вертикальной прокрутки, формат 16:9, шапка не выше 10 % высоты, блок показателей

| Полоса | Правило | При 1080 px | Что внутри |

Правило «один экран без вертикальной прокрутки» я соблюдаю на широком мониторе

## 2. Шапка

Показывает три вещи: кто на смене, когда был последний расчёт и сколько он занял.

```sql
SELECT started_at, finished_at,
       (extract(epoch FROM finished_at - started_at))::int AS sec
FROM   pred.run
WHERE  status = 'done'
ORDER  BY run_id DESC
LIMIT  1;
```

Длительность расчёта на экране — не украшение. В постановке записано «время
формирования прогноза менее 5 минут», и если число поползёт вверх, диспетчер
увидит это раньше нас. Таблица `pred.run` хранит разбивку по стадиям
(`ms_fetch`, `ms_aggregate`, `ms_features`, `ms_inference`, `ms_explain`, `ms_write`),
так что при выходе за бюджет сразу видно, какая стадия распухла.

В макете стоит «38 с». Реальное значение узнаем только на продуктивном объёме:
по нашему расчёту бюджета (HLD, разд. 8.2) целевое 41 секунда при потолке 155.

## 3. Полоса показателей

### 3.1. Критический риск — 6 объектов

```sql
SELECT count(*) FILTER (WHERE risk_rank = 1) AS now_critical
FROM   pred.forecast_current;
```

Сравнение «вчера было 4» берём из прогона, ближайшего к этому же времени сутки назад:

```sql
SELECT count(*) FILTER (WHERE f.risk_rank = 1)
FROM   pred.forecast f
JOIN   pred.run r USING (run_id)
WHERE  r.run_id = (SELECT run_id FROM pred.run
                   WHERE status = 'done'
                     AND started_at <= now() - interval '24 hours'
                   ORDER BY started_at DESC LIMIT 1);
```

Число без вчерашнего значения мертво: «шесть объектов» само по себе не говорит,
хорошо это или плохо. «Шесть, вчера было четыре» уже требует действия.

### 3.2. Прогнозов за 24 ч — 37, подтвердилось 12 из 15 закрытых

```sql
SELECT count(*) AS issued
FROM   pred.forecast f JOIN pred.run r USING (run_id)
WHERE  r.started_at >= now() - interval '24 hours';
```

**Здесь у нас дыра в схеме.** Вердикта диспетчера («подтвердилось» / «ложная»)
хранить негде: таблицы под обратную связь в `db/migrations/004_events.sql` нет. Её надо завести:

```sql
CREATE TABLE pred.feedback (
  forecast_id  bigint      NOT NULL,
  section_id   integer     NOT NULL,
  verdict      smallint    NOT NULL,   -- 1 подтвердилось, 0 ложная
  reason_code  text,                   -- оборудование / датчик / модель / человеческий фактор
  comment      text,
  decided_at   timestamptz NOT NULL DEFAULT now(),
  decided_by   bigint      NOT NULL
);
```

Четыре кода причины закрытия я беру не с потолка: ровно такую классификацию
требовал модуль инцидентов в проекте En+, и она же разделяет «сломалось
оборудование» и «наврала модель». Без этого разделения нельзя понять, ухудшается
модель или ухудшается парк.

### 3.3. Темп тревог — 4,2 в час при норме 6

```sql
SELECT round(count(*)::numeric
             / greatest(extract(epoch FROM now() - :shift_start) / 3600, 1), 1)
FROM   smvu.event
WHERE  event_time >= :shift_start;
```

Порог 6 — из ISA-18.2, это предельно управляемая нагрузка на одного оператора.
Норматив абсолютный, на человека, а не на километр. При 825 км и участках по 200 м
у нас 4125 участков, и укладывание в норму означает одну тревогу с участка
раз в 28 дней. Отсюда следствие для архитектуры: четыре направления прогноза
нельзя сажать на одну общую ленту без квот.

### 3.4. Заявки на ТО — 9, принято 7, отклонено 2

```sql
SELECT count(*)                                                      AS created,
       count(*) FILTER (WHERE status IN ('IN_PROCESS','COMPLETED'))  AS accepted,
       count(*) FILTER (WHERE status = 'CANCELLED')                  AS rejected
FROM   maint.notification
WHERE  created_at >= now() - interval '24 hours'
  AND  source_system = 'forecast';
```

**Своих заявок от чужих отделяем колонкой `source_system`, которая в таблице уже
есть.** В `db/migrations/001_assets.sql`, строка 628, у неё значение по умолчанию
`'manual'` — то есть заявка, заведённая диспетчером руками. Автозаявка пишется
со значением `'forecast'`. Новую колонку `origin` заводить не надо, это была бы
вторая колонка того же смысла.

**Статусы берём те, что объявлены в схеме:** `OPEN`, `IN_PROCESS`, `COMPLETED`,
`CANCELLED`. Отдельных `accepted` и `rejected` у заявки нет, поэтому «принято» —
это взятые в работу и выполненные, а «отклонено» — отменённые.

Доля отклонённых — честный индикатор доверия. Если из девяти заявок отклоняют
восемь, модель не работает, какими бы ни были Precision и Recall на отложенной выборке.

### 3.5. Точность и полнота — 0,78 / 0,56

Считаются методикой из `code/predictive_metrics.py`, функция
`evaluate_alerts()`, скользящее окно 30 суток. Предупреждение засчитывается,
если выдано не позже чем за 24 часа до отказа и не раньше верхней границы окна.

Отказ берём из журнала неисправностей ОДС, а не из журнала сработок — об этом
подробно в разделе 6.2.

Пороги 0,70 и 0,50 на плитке подписаны намеренно: число без порога не читается.

### 3.6. Нет данных — 23 датчика молчат больше 6 часов

```sql
SELECT count(*)
FROM   smvu.sensor s
WHERE  s.is_active
  AND  NOT EXISTS (SELECT 1 FROM smvu.reading r
                   WHERE r.sensor_id = s.sensor_id
                     AND r.read_time > now() - interval '6 hours')
  AND  NOT EXISTS (SELECT 1 FROM permit_detector_inhibit i
                   WHERE i.sensor_id = s.external_id
                     AND now() BETWEEN i.inhibited_from
                                   AND coalesce(i.inhibited_to, 'infinity'));
```

Второе условие критично. По базе опасностей Ямал СПГ среди мер контроля к
опасностям «Открытое пламя» и «Электродуговая сварка» стоит прямое указание
«Заблокируйте датчики пожара и дыма». То есть датчик молчит штатно, под наряд,
и показывать его как неисправный — ложная тревога, которую мы создали сами.

Отдельная плитка нужна потому, что по Регламенту молчащий датчик — это
самостоятельная неисправность, а не отсутствие событий. Закрасить его зелёным
вместе со спокойными участками означает спрятать отказ.

## 4. Схема коллектора

### Что показывает

Линейную схему участка: камеры квадратами, вентшахты отводами вниз, участки между
камерами — отрезками, окрашенными по риску. Над проблемными объектами — маркеры
с формой и цифрой.

### Почему схема, а не карта

Коллектор — линейный объект. Диспетчеру важнее порядок пикетов и то, между какими
камерами лежит проблемный участок, чем географическая точность. Такой же взгляд
«узлы и участки» даёт ZuluGIS, специализированная ГИС для инженерных сетей.
Карта города остаётся отдельным экраном, как и записано в постановке задачи.

### Как считается

Геометрия и топология — из `db/migrations/002_geo.sql`: `geo_object` (объекты),
`network_edge` (участки узел-ребро), `object_risk` (текущий риск объекта).

Риск участка — **максимум** по объектам на нём, а не среднее:

```sql
SELECT e.edge_id,
       max(l.sort_order) FILTER (WHERE l.code <> 'no_data')      AS edge_rank,
       bool_or(r.risk_code IS NULL OR r.risk_code = 'no_data')   AS has_gaps
FROM   network_edge e
JOIN   geo_object o
         ON o.object_id IN (e.object_id, e.from_node_id, e.to_node_id)
LEFT   JOIN object_risk r ON r.object_id = o.object_id
LEFT   JOIN risk_level  l ON l.code      = r.risk_code
GROUP  BY e.edge_id;
```

Три вещи в этом запросе неочевидны, и каждая — про то, как устроена схема.

**Объекты участка берём через три ссылки, а не через колонку `edge_id`.** Её
в `geo_object` нет: в `db/migrations/002_geo.sql` связь обратная — у ребра есть
`object_id` (собственная запись ребра как объекта) и два конца `from_node_id`,
`to_node_id`. Поэтому объекты участка — это его собственная запись и две камеры
по краям.

**Ранг берём из `risk_level.sort_order`**, колонки `risk_rank` в `object_risk`
не существует, там `risk_code` и `score`.

**`no_data` исключаем из максимума.** В справочнике порядок такой: `low` 1,
`medium` 2, `high` 3, `no_data` 4. Наивный `max` дал бы участку с одним
объектом без данных ранг 4 — выше, чем «высокий риск». Дыра в данных
покрасилась бы как худшее состояние. Поэтому `FILTER` по максимуму
и отдельный флаг `has_gaps`: отсутствие данных показываем штриховкой,
а не цветом риска.

Правило максимума задано нормативом, а не выбрано нами: пункт 4.4.6 Регламента
говорит «достаточно наличия одного из наиболее опасных повреждений». Интуитивно
рука тянется усреднять — и это была бы ошибка: участок с одним аварийным объектом
и девятью исправными усреднился бы в «почти нормальный».

Участок, где `edge_rank` пустой (телеметрии нет), рисуется пунктиром в цвете
«нет данных». Заливать его зелёным было бы враньём.

### Пять состояний, различимых без цвета

| Состояние | Знак | Заливка (светлая тема) |
|---|---|---|
| Критический | ▲ 1 | `--risk-critical` `#A81F16` |
| Высокий | ◆ 2 | `--risk-high` `#B35C00` |
| Средний | ● 3 | `--risk-medium` `#F2C200` |
| Низкий | ○ 4 | `--risk-low` `#E4EDE7` |
| Нет данных | штриховка + ? | `--risk-nodata` `#C9CFD6` |

Форма и цифра нужны потому, что около 8 % мужчин не различают красный и зелёный,
а в диспетчерской мужчин обычно большинство. Проверка простая: распечатать экран
на чёрно-белом принтере — смысл должен сохраниться. В `docs/acceptance-test.md` это
строки НФ-48 и НФ-52.

## 5. Топ-10 по риску

```sql
SELECT f.risk_rank, f.probability, f.factors,
       e.equipment_no, e.name
FROM   pred.forecast_current f
JOIN   asset.equipment e ON e.id = f.section_id
ORDER  BY f.probability DESC
LIMIT  10;
```

Строка «основание» под кодом объекта собирается из поля `factors jsonb`, куда
модель кладёт вклад признаков. Это закрывает требование объяснимости: диспетчер
видит «уход нуля 0,23 % при норме ±0,2 %», а не одно число вероятности.

### Почему именно десять

В практике управления тревогами десяток самых «болтливых» источников даёт
от 60 до 80 % всего потока. Такой список собирается простым запросом до всякой
модели и начинает приносить пользу с первой недели — это наш самый дешёвый
первый результат.

### Как считается вероятность

Итоговая оценка собирается из нескольких независимых сигналов считалкой
`code/signal_fusion.py`. Она возвращает две величины, и это принципиально:

- **оценка** — нормированная, ею сравниваем объекты между собой;
- **уверенность** — ненормированная, она не может вырасти оттого, что один
  из источников пропал.

Пример из самопроверки скрипта. Камера, газ даёт 0,85 за отказ, климат 0,30,
здоровье датчика 0,20, история ремонтов 0,70, наряда-допуска нет:

```
0,30·0,85 + 0,20·0,30 + 0,15·0,20 + 0,20·0,70 = 0,485
```

Уверенность 0,485, оценка 0,571 — случай уходит в автоматическую обработку.
Уберём всё, кроме газоанализатора: оценка подскочит до 0,85, а уверенность
упадёт до 0,255, и правило отправит случай человеку. Один датчик в одиночку
заявку не заводит.

### Два уровня реакции вместо одного порога

Конфликт между Precision 0,7 и Recall 0,5 снимается не подбором среднего порога,
а разведением на два уровня:

| Уверенность | Что делает система | Что считаем |
|---|---|---|
| высокая | заводит заявку `maint.notification` | Precision по автозаявкам |
| средняя | кладёт в список наблюдения, заявки нет | Recall по обоим уровням |

## 6. Журнал прогнозов

### Что на экране

Шесть последних прогнозов: время, объект, направление, основание, упреждение
и вердикт. У незакрытых — две кнопки, «Подтвердилось» и «Ложная».

```sql
SELECT r.started_at, e.equipment_no, f.direction, f.factors, f.horizon_h,
       fb.verdict, fb.reason_code
FROM   pred.forecast f
JOIN   pred.run r      USING (run_id)
JOIN   asset.equipment e ON e.id = f.section_id
LEFT   JOIN pred.feedback fb ON fb.forecast_id = f.forecast_id
ORDER  BY r.started_at DESC
LIMIT  50;
```

### Почему кнопка вердикта — не украшение интерфейса

В работе Силезского политеха (Sensors, 2021) над детектором выбросов поставили
лес решающих деревьев — 40 деревьев глубиной 8, — обученный **на вердиктах
оператора**, и сняли 90,25 % ложных тревог. Эти две кнопки — источник обучающих
данных для второго слоя модели, и закладывать их надо с первого дня, а не
«добавим потом».

Поэтому же вердикт пишется с кодом причины: оборудование, датчик, модель,
человеческий фактор. Иначе мы будем знать, что прогноз не сбылся, но не будем
знать почему.

### Колонка «Упреждение»

Разница между временем выдачи прогноза и временем отказа. Для незакрытых —
прочерк, потому что отказа ещё не было.

**Тонкость, на которой я уже споткнулась.** В `predictive_metrics.py` проверка
упреждения была тавтологичной: функция отбирала совпадения с упреждением
не меньше горизонта, а потом проверяла, что минимальное упреждение не меньше
того же горизонта. Провалиться она не могла. Исправлено: при горизонте, равном
порогу, функция возвращает `None` — «не измерено» — вместо `True`. Реально
померить упреждение можно только прогоном с нулевым горизонтом:

```
horizon=24 -> lead_time: None   min_lead 72.0   ← не измерено
horizon=0  -> lead_time: False  min_lead 6.0    ← настоящий минимум
```

## 7. Качество и нагрузка

### Четыре числа

| Показатель | Формула | Источник |
|---|---|---|
| Точность | TP / (TP + FP) | `evaluate_alerts()`, окно 30 сут |
| Полнота | TP / (TP + FN) | там же |
| Упреждение, медиана | медиана по совпадениям | там же, поле `median_lead_hours` |
| Ложных на 1000 объекто-суток | FP / объекто-сутки × 1000 | там же |

Последний показатель нужен потому, что абсолютное число ложных тревог растёт
вместе с парком и ничего не говорит. Нормировка на объекто-сутки позволяет
сравнивать месяцы между собой и до/после дообучения.

### Линия темпа тревог за смену

Почасовые отсчёты плюс пунктир норматива на шести:

```sql
SELECT date_trunc('hour', event_time) AS h, count(*)
FROM   smvu.event
WHERE  event_time >= :shift_start
GROUP  BY 1 ORDER BY 1;
```

Значение без тренда — плохая практика. По линии видно не только текущие 4,2,
но и было ли за смену приближение к пределу.

**Ни одного гейджа и ни одной круговой диаграммы** на экране нет намеренно:
у «спидометров» очень низкая плотность данных, пол-панели на одно число.

## 8. Что надо получить от АО «Москоллектор»

Ниже — то, без чего макет остаётся макетом. По каждому пункту: что просим,
зачем и что сломается без этого.

### 8.1. Месячная выгрузка СМВУ — просить первой

**Что:** события за любой полный месяц в том виде, в каком выгружается сейчас
(ID датчика, время, тип, адрес, результат проверки).

**Зачем:** сейчас у нас вилка по частоте событий **в 5 раз**, от 18,1 до 90,4 млн строк за 12 лет. От неё зависит
всё: объём базы (18 или 90 млн строк), нужна ли TimescaleDB, влезаем ли в 5 минут,
и сколько тревог в час реально увидит диспетчер.

**Без этого:** все оценки производительности остаются предположениями,
и на защите их нечем подтвердить. Одна выгрузка и полчаса работы закрывают вопрос.

**Первая же проверка на этих данных:** построить распределение интервалов между
соседними записями. Если интервалы рваные — записи оставляли только по факту
изменения, и тогда среднее по строкам считать нельзя, надо интерполировать
ступенькой. На Ямале в PI System сжатие отключали намеренно именно из-за этого.

### 8.2. Журнал неисправностей датчиков ОДС с полем «результат проверки»

**Что:** журнал неисправностей, а не только журнал сработок.

**Зачем:** в инструкции по проверке защит отказ делится на два вида. «Ложное
действие» — датчик сработал зря, это видно сразу. «Несрабатывание» — датчик
промолчал, когда должен был сработать. Второй вид в истории сработок **невидим**:
молчащий датчик выглядит как здоровый.

**Без этого:** положительный класс для направления «отказ датчика» взять неоткуда,
и Recall мерить не на чем.

**Хорошая новость:** по таблице 12.1 Регламента СМВУ передаёт наверх две
независимые строки — «Состояние датчиков газа: сработал / не сработал» и
«Функционально-техническое состояние аппаратуры: исправна / неисправна».
Второй признак, возможно, уже есть в выгрузке. Надо проверить.

### 8.3. Справочник датчиков

**Что:** по каждому датчику — ID в СМВУ, тип и модель (ДМТ-6, СИГМА-1, БСМ, ТК-1,
СЕНСИС-500, МОД, ГАСБ), место установки в адресации СМВУ, дата ввода,
дата последней поверки, межповерочный интервал.

**Зачем сразу три вещи:**

1. **Тип определяет порог.** Пункт 11.3.2 задаёт допустимый уход нуля отдельно
   для каждого типа: ДМТ-6 и СИГМА-1 ±0,2 %, БСМ ±0,25 %, ТК-1 и СЕНСИС-500 ±0,3 %,
   МОД ±0,22 %, ГАСБ ±0,1 %. Одним числом не обойтись.
2. **Принцип измерения определяет поведение.** У оптического МОД порог метана
   0,88 %, у остальных 1,0 %, и у МОД есть встроенная самодиагностика, а у
   термокаталитического ДМТ-6 нет. Без признака «тип датчика» МОД будет
   срабатывать раньше соседей и выглядеть шумящим.
3. **Просроченная поверка — сильнейший признак.** Регламент межповерочный интервал
   не задаёт, отсылает в Госреестр, но годовой цикл выводится: поверка входит
   в состав текущего ремонта аппаратуры контроля метана, а он раз в год.

**Без этого:** пороги придётся подбирать эмпирически и обосновывать их будет нечем.

### 8.4. Окна планово-предупредительного ремонта

**Что:** когда какой датчик стоял на ППР и когда его выводили из работы под наряд.

**Зачем:** пункты 11.5.14–11.5.21 в каждом описании текущего ремонта начинаются
строкой «включение/отключение режима ППР в СМВУ». Значит в истории есть периоды,
когда датчик молчал не потому что сломался.

**Без этого:** модель выучит график ремонтов вместо отказов. Это не теория —
ровно так выглядит классическая утечка целевой переменной.

**Где искать:** в АРМ-Контроле этого скорее всего нет, надо смотреть журналы ОДС.

### 8.5. Выгрузка АРМ-Контроль

**Что:** реестр допусков и заявок на работы. Критично **время с точностью
до часа**, а не до даты, и код места работ.

**Зачем:** пожарный риск строится на корреляции с огневыми работами. По пункту
28.3.7 Регламента после огневых работ приёмка места не ранее чем через 30 минут,
затем наблюдение **не менее 4 часов** — это и есть наше окно признака. Плюс
радиус оповещения соседей 15 м и радиус изоляции кабелей при электросварке 20 м
дают пространственную привязку.

**Без точного времени:** наряд на сутки «покрывает» любое срабатывание в эти сутки,
и признак становится бесполезным.

**Отдельно надо спросить:** совпадает ли код места работ с адресацией датчиков
СМВУ. Если адрес записан текстом, сопоставление станет главным источником ошибок,
и под него придётся закладывать отдельную работу.

**Машинный признак «авария или план»** уже есть: у аварийного ремонта
допускающий проверяет номер аварийной телефонограммы ОАТИ, у планового — ордер.
У плановой записи этого поля просто нет.

### 8.6. Реестр оборудования ОЭ с историей ремонтов

**Что:** объекты по районам (вентшахты, насосы, камеры, люки), даты ввода
в эксплуатацию и — обязательно — **даты капитальных ремонтов**.

**Зачем:** у насоса нормативный срок службы 8 лет, а капремонт положен каждые 6.
Значит возраст надо считать от последнего капремонта, иначе отремонтированный
и нетронутый восьмилетние насосы попадут в одну корзину.

**Что уже есть в нормативе:** приложения 3 и 4 Регламента дают минимальную
продолжительность эффективной эксплуатации по каждому элементу. Зная дату ввода
и норматив, выработку ресурса в процентах считаем сразу — этот признак
изобретать не надо, он записан.

### 8.7. Акты визуальных обследований

**Что:** результаты осмотров с описанием дефектов.

**Зачем:** таблица 4.2 Регламента — это по сути готовый размеченный справочник
на 37 строк. Осмотрщик пишет «продольные трещины вдоль рабочей арматуры
с раскрытием 1,0–3,0 мм», и таблица присваивает III категорию и мероприятие
«Восстановление». То же наблюдение с раскрытием до 1,0 мм — уже II категория
и профилактика. Один миллиметр отделяет профилактику от ремонта.

А таблица 4.1 даёт числовые границы категорий: коррозия арматуры 2 / 7 / 15 / 25 %
и исчерпание несущей способности 10 / 33 / 67 %. Это **готовая целевая переменная**
для направления «износ», причём с нормативными порогами, а не подобранными нами.

**Тонкость при разметке:** пункт 19.1.6 вводит общие осмотры весной и осенью,
причём весенний уточняет план текущего года, а осенний — следующего. Значит
осенние дефекты в данных будут выглядеть как «нашли и не починили», хотя
по регламенту их и не должны были чинить в том же году. Не учтём — модель
решит, что осенью ремонт срывается.

### 8.8. Инструкция диспетчера ОДС

**Что:** действующий порядок действий при срабатывании.

**Зачем:** в Регламенте его нет — пункт 3.7 отсылает к ПТЭКК и приказам
руководителя. Единственный пошаговый алгоритм в документе (пункт 24.5.1)
адресован людям в коллекторе, а не диспетчеру.

**Без этого:** журнал прогнозов и модуль заявок мы спроектируем по своему
представлению, а не по тому, как человек работает сейчас.

### 8.9. Формы журналов

**Что:** бланки с графами. В Регламенте названы двенадцать журналов, но ни одной
формы с полями не приведено.

**Зачем:** это прямая структура наших таблиц. Мы реконструировали состав полей
реестра допусков из требований разных пунктов — это гипотеза, её надо сверить.

### 8.10. Какое железо стоит у диспетчеров

**Что:** модель компьютера, версия браузера, разрешение монитора, ширина канала
до диспетчерского пункта.

**Зачем:** весь наш расчёт производительности построен на предположении, что
техника старая. Косвенное подтверждение есть: ГОСТ Р 22.1.12 пункт 5.4 требует
монитор не меньше 395 мм по диагонали, разрешение не ниже 1280×1024 и частоту
75 Гц — это характеристика эпохи электронно-лучевых мониторов.

**Что от этого зависит конкретно:** с версии 6.0 библиотека MapLibre требует
WebGL2 обязательно, а Chrome с вехи 139 убирает программную подмену. На старой
встроенной видеокарте карта может просто не открыться. Поэтому в макете Leaflet
(42 КБ, без WebGL), а не MapLibre (206–283 КБ).

### 8.11. Правила технической эксплуатации коллекторов

**Что:** документ ПТЭКК, на который Регламент ссылается.

**Зачем:** там периодичность обходов, пороги загазованности и нормативы
реагирования. В открытом доступе сайты отдают его с ошибкой 403.

| Сейчас в макете | Откуда возьмётся настоящее | Что может измениться |
|---|---|---|
| 6 объектов в критической зоне | `pred.forecast_current` | порог критической зоны придётся калибровать: если в красную попадёт треть парка, сигнал мёртв |
| темп 4,2 тревоги в час | `smvu.event` за смену | вилка в 5 раз, 18,1 против 90,4 млн строк; при верхней границе понадобятся квоты |

| 8 участков на схеме | `network_edge` | 4125 участков не поместятся: понадобится выбор коллектора и уровень «район → коллектор → участок» |
| коды вида `МК.03.К127.0415` | реестр ОЭ | наша маска — предложение; настоящая адресация у заказчика своя, и под неё придётся переделать |
| типы датчиков в топ-10 | справочник датчиков | список типов может отличаться от того, что в Регламенте |
| «упреждение 31 ч» | `pred.feedback` + журнал отказов | мерить придётся прогоном с нулевым горизонтом, см. раздел 6 |

Отдельно про схему коллектора. Восемь участков на экране — это фрагмент.
Когда придёт реестр, понадобится навигация по уровням: район, коллектор, участок.
Показать 4125 участков одной лентой нельзя, а показать только «плохие» —
значит потерять контекст, где они находятся относительно друг друга.

## 10. Чего на экране нет намеренно

- **Гейджей и круговых диаграмм.** Пол-панели на одно число — слишком дорого
  при бюджете 3,3 минуты на тревогу.
- **Тепловой карты «участок × час».** Она полезна, но её место — экран карты,
  а не сводка. На дашборде она съест ряд целиком.
- **Прогноза остаточного ресурса в месяцах.** На отраслевом совещании прямо
  сказали, что в общем виде эта задача не решена ни у кого. Обещаем повышенный
  риск на горизонте, как и записано в постановке, а не «осталось три месяца».
- **Общей ленты всех тревог.** По расчёту бюджета ISA-18.2 четыре направления
  на одной ленте дают до 590 тревог в сутки при норме 144.
