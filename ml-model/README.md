# Исходники ML-кандидата: draft, не готов к выпуску

Этот каталог переносит существующий код кандидата от 22.09.2026 для отдельного
ревью. **Кандидат обучался на 720 часов. Решение команды от 23.09.2026 требует
24 часа; задача MOS-219 остаётся открытой.** Исходники не исправляют этот дефект
и не разрешают менять горизонт стенда на 720. Кандидат нельзя выпускать или
подключать к продуктовому compose. Замена подписи `720` на `24` не переобучает модель.

Отдельно остаётся MOS-217: нужна детализация прогноза до датчика или хотя бы участка.
Текущий кандидат выдаёт риск на коллектор. Точная привязка каналов к дереву и ранжирование
участков не являются проверенной моделью риска участка; эту задачу данный PR не закрывает.

Здесь находятся код расчёта, признаков, обучения, экспорта, проверки и HTTP-сервиса.
Веса, клиентские CSV/Parquet, реестр каналов, готовые прогнозы, журналы и результаты
экспериментов в PR не входят. Продуктовые `contracts/` остаются источником действующей
границы; описанный здесь collector-контракт — предложение прежнего кандидата,
которое нужно отдельно согласовать после работы над MOS-219.

## Состав и границы

- `ml-model/src/ml/` собирает D5, признаки и моменты решения. `collector_identity.py`
  связывает канал с родителем его объекта в дереве заказчика, без голосования префиксов.
- `ml-model/src/ml/serving/` загружает веса, проверяет горизонт и порядок признаков,
  обслуживает `/model`, `/predict`, `/health`. Отсутствие модели останавливает запуск.
- `ml-model/autoresearch_v3/` содержит три неизменённых файла прежнего обучения.
- `ml-model/scripts/ml_v3_collector_release.py` — прежний рецепт сборки и обучения
  **720-часового** кандидата. Он сохранён для ревью; в этой задаче его не запускали.
  `ml_v3_export.py` и `ml_v3_holdout.py` нужны ему как модули с общими функциями.
  Их старые самостоятельные команды и слова «holdout/one look» не означают,
  что у collector-кандидата появился независимый holdout.
- `ml-model/scripts/ml_v3_score.py` рассчитывает архивный срез и сохраняет историю
  предупреждений с исходными вероятностью и признаками. Пустой `--check`, неверный
  горизонт, дата за границей наблюдений и пустое окно не дают успешного результата.
- `ml-model/requirements/` сохраняет закреплённые зависимости образов. Для проверок
  нужен `requirements/ml-test.txt` (включает pytest и httpx). Dockerfile используют контекст **ml-model/**, но без
  отдельно предоставленных весов образы не собираются. Продуктовое развёртывание
  этот draft не меняет.
  `ml-serving-licenses.md` — исторический аудит прежнего образа, не проверка нового
  окружения; комментарии о выпуске в скопированных рецептах относятся к прежнему кандидату.

## Проверка исходников без клиентских данных

Все относительные пути Python отсчитываются от `ml-model/`:

```sh
cd ml-model
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src:scripts python -c \
  'import ml_v3_collector_release, ml_v3_score; from ml import v3_score; v3_score.load_code()'
PYTHONDONTWRITEBYTECODE=1 python -m pytest tests/ml -q -p no:cacheprovider
```

Проверки реальных весов и данных явно пропускаются, если их нет. Это проверка
упаковки и доступных контрактов, а не повторная оценка качества или доказательство
работоспособности 24-часовой модели. Исторический Q2 уже использовали при разработке;
независимой контрольной выборки у этого кандидата нет. Результаты прошлых прогонов
не копируются в PR и не превращаются в доказательство для новой модели.

## Внешние файлы

`ml-model/docs/external-artifacts.json` содержит имена, размеры и SHA-256 существующих
внешних файлов кандидата; содержимого там нет. Проверяющий получает их отдельно
по разрешённому каналу и сверяет каждый файл до локального исследования.
`ml-model/docs/source-manifest.json` позволяет проверить, что перенесённый алгоритм
совпадает с исходным кандидатом. Единственная адаптация скопированного теста — явная
имитация ошибки чтения для проверки её обработки без клиентского журнала; в manifest
сохранены оба хеша этого файла. Алгоритм и замороженные файлы обучения не менялись.
Никакие symlink на рабочие данные не создаются.

Перечень внешних входов и ограничения находятся в
`ml-model/docs/external-inputs.md`. Переобучение, новый порог и новая проверка на 24 часа
должны быть отдельной работой по MOS-219; этот draft не утверждает, что она выполнена.
