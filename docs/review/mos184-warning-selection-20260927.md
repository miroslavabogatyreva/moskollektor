# MOS-184: первый выбор участков предупреждения

Основа: `origin/master` c708321774925830892bb72c28ef38b9eedc6c29.
Запрос Мирославы от 27 сентября: отдельный перенос из PR #12, миграция 050,
лимит 3, сохранение действующего горизонта 720 ч.

## Что изменено

`план_заявок()` сохраняет выбранные участки, маршрут и исходные поля предупреждения
в `pred.warning_order_selection`. Первичный ключ `(pfx, opened_at)` разрешает один
первый выбор: при гонке второй процесс ждёт вставку первого и читает её результат.
Повторы используют существующие ключи заявок и их уникальный индекс.

Миграция 050 ставит `order_top_sections_per_object=3`. Предупреждения, по которым
уже есть заявки, запечатываются без дополнения. Старые превышения не удаляются,
даже если у предупреждения уже четыре заявки. Решение об очистке принадлежит
Мирославе. Новое открытие того же префикса получает свой набор участков.

Выбор сохраняется перед публикацией прогнозов, после проверки свежести score.json.
При неудачной записи заказа транзакция отменяет заявку и заказ; следующий прогон
повторяет сохранённый выбор. При отсутствии выбранного участка в текущем прогоне
система не заменяет его новым участком. Явный `--rollback` отменяет также снимок.

Формат прогноза, модель, горизонт 720 ч, срок от обнаружения (MOS-179), карта и API
не менялись. Полный PR #12 не переносился.

## Проверка

`backend/tests/test_warning_selection.py` создаёт отдельную локальную базу со
всеми 45 миграциями, имитирует прежние заявки перед 050 и удаляет только эту базу.
Путь `план_заявок → publish.записать → завести` использует настоящие PostgreSQL,
уникальные ограничения, прогнозы, заявки и заказы. Данные синтетические, без ML.
Проверки охватывают смену рейтинга, повторы, конкуренцию двух соединений,
повторное открытие, исторические 1/4 заявки, сбой записи заказа, изменение лимита,
пустой первый отбор и временно отсутствующий выбранный участок.

Команда запуска (DSN только выделенного локального PostGIS):

```sh
MOS184_TEST_DSN=postgresql://postgres:mos184_test@127.0.0.1:55484/postgres \
  python3 -m pytest backend/tests code/tests -q
python3 code/check_schema.py
python3 code/check_deploy_set.py
python3 code/check_stale_fetch.py
(cd backend && python3 -m app.domain.order_rules)
```

Независимый обзор: блокирующих дефектов не найдено; замечания о проверках rollback,
неполного отбора и исторических заявок включены в регрессионные тесты.

Итоговый запуск: **95 passed, 2 skipped**, 2.24 с. Два пропуска — существующие
опциональные ingest-тесты; все девять новых проверок выполнены. Проверки схемы,
состава выкладки, stale-fetch и самопроверка order_rules прошли.

Красная проверка: исходный `order_rules.py` из master c708321 загружен отдельно
в память без изменения рабочей копии. После первых трёх заявок и переворота весов
ожидался пустой повторный план; исходный код вернул три новых ключа участков 4, 5, 6
того же предупреждения. Тест упал именно на этом утверждении. Исправленная версия
прошла его, включая отдельный случай настоящего изменения SQL-весов по D5.

Проверка устаревшего score вызывает `worker.прогон()` с подставленным ответом
стадии модели: результат failed, снимков и заявок нет. Это проверяет порядок
проверки свежести; сам инференс модели и внешний ML-сервис не запускались.

## Выкладка и предел проверки

Этот отчёт подтверждает локальную регрессию, а не приёмку стенда или ML-качество.
Миграция накатывается перед заменой worker. После выкладки должны работать только
новые worker: старый код не читает снимок и всё ещё способен менять выбор.
На стенде повторить М-10 и два прогона с изменением весов и откатом. Исторические
превышения могут оставить М-10 красным до отдельного решения об их очистке.
Откат к старому worker возвращает дефект; новую таблицу можно оставить, но удалять
снимки у уже выданных предупреждений нельзя. Production в этой работе не менялся.
