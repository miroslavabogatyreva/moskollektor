# Продуктовая интеграция предупреждений и реального дерева: draft

Основа: master 658b150 от 23.09.2026. Эта ветка переносит проверенные локальные исправления с сохранением сегодняшних доработок команды. Она не выпускает модель и не закрывает MOS-219/MOS-217.

## Поведение

- `score.v3` принимает настоящие collector_id и полную историю предупреждений. Вероятность, признаки, момент открытия и выбранные участки сохраняются один раз. Новая заявка не зависит от разреженного журнала прогнозов.
- Блокировка предупреждения и транзакция предотвращают дубли при повторном/конкурентном worker. Если создание наряда не состоялось, предупреждение и уведомление откатываются вместе.
- Срок предупреждения привязан к его исходному открытию. Сохранены сегодняшние нормативы 16/48/72 ч и ограничитель `order_preventive_cap_h`. Обычный старый путь сохраняет текущую семантику master.
- Карта сохраняет разные линии префиксов, доступные формы риска, клавиатурные переходы и сегодняшние E 2E. Неоднозначный участок 798:0 показан отдельно. Вероятность коллектора не выдаётся за вероятность участка.
- Метаданные модели и horizon проверяются на границе. Производственный путь нового collector-контракта отклоняет 720 ч: действует решение MOS-219 о 24 ч. Замена настройки или подписи не меняет целевую метку.
- `ml-score.sh` требует явно указать образ, каталог данных, режим live/archive и срез. В live проверяется подтверждённая граница данных; результат публикуется атомарно перед worker. Скрипт сам не доказывает норматив всей потоковой цепочки.

## Решения, без которых нельзя выпускать

1. **MOS-219:** нужна обученная и проверенная модель 24 ч. Исторический 720-часовой кандидат не подходит. Нельзя включать его на стенде через изменение подписи. Перед запуском принятой модели настройка `forecast_horizon_h`, score и model metadata должны совпадать и быть 24.
2. **MOS-217/MOS-154:** по уточнению Мирославы в Telegram 23.09 нужен прогноз до датчика, минимум до участка. Здесь исправлена идентичность объектов и раскрыт масштаб вероятности; модель ниже коллектора не разработана.
3. **MOS-182:** предложено хранить отдельную заявку на каждое предупреждение, а не схлопывать открытия на одном участке. Это вариант для ревью владельцем продукта; существующая задача обсуждает и другой вариант.
4. **MOS-179:** срок от исходного открытия не сдвигается при поздней обработке. Полезность сроков на принятой 24-часовой модели ещё надо измерить.
5. **MOS-184:** число выбранных участков фиксируется при первом создании. Для теста установлен лимит 2; текущий master по умолчанию имеет 0 («все»). Этот PR не меняет его. Ограниченный объём заявок на стенде требует явного решения и настройки; результат 352 заявки не обещается для default 0.
6. Отказ от старого prefix score является изменением контракта. Устанавливать ветку отдельно от принятого нового экспортера и metadata нельзя.

## Миграции и проверка

Добавлены только 041_warning_orders.sql и 042_collector_d 5_weights.sql. Уже применённые 037–040 не меняются. Прежняя локальная 039, которая переводила настройку на 720 и меняла лимит заявок, не переносилась.

На новой пустой тестовой базе успешно накатились все 38 миграций. Загружены реальные справочники:95 объектов,11485 каналов,3173 участка. Связанные модули прошли 90 тестов без пропусков. Фронтенд собран, шесть selfcheck прошли.

Низкоуровневое воспроизведение старых 720-часовых предупреждений:176 открытий → 352 заявки при тестовом лимите 2; конкурентные повторы дают 0 новых. Проверены исходные значения, JSONB, разные открытия в один день, откат при отсутствующем справочнике и при отказе вставки наряда. Это проверка механизма сохранения; производственный worker 720 ч отклоняет.

Для интерфейса в свежую тестовую базу скопирован реальный архивный снимок 3172 прогнозов из прежней изолированной базы. Исходные вероятности, модель, горизонт 720 ч и дата сохранены. Это архивный UI-fixture, не результат принятой 24-часовой модели. Исходная база читалась без изменения. Все четыре неизменённых E2E прошли за 10,2 с против итогового API и свежей базы.
