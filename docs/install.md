# Как развернуть стенд с нуля

Инструкция для человека, у которого есть только чистая машина Debian/Ubuntu
и доступ по SSH — ни Docker, ни репозитория, ни `.env` на ней ещё нет. Она
охватывает то, чего нет в `deploy/README.md`: саму машину, сеть вокруг неё
и резервные копии. Три шага docker compose — TLS, пароль базы, `up -d` —
подробно разобраны в `deploy/README.md`, здесь на них только ссылка, чтобы
не держать одно и то же в двух файлах. Проверено на сервере заказчика
`135.106.216.101`, Ubuntu 24.04.4 LTS — факты и учётки того сервера
в `docs/server.md`.

## 0. Что именно разворачивается и на какой версии базы

**Развёртывать эту систему будем не мы.** 19.09.2026 заказчик написал: «Формат сдачи -
это пакет, который можно распаковать и запустить, с обязательной инструкцией
по развертыванию», и отдельно — «организаторы будут разворачивать на своих мощностях
для оценки» (`docs/meetings/2026-09-19-ответы-заказчика.md`, сводные 18 и 10). Значит
инструкция читается человеком, который наш репозиторий видит впервые и спросить у нас
не может. Всё, что в ней описано, должно работать без нашего присутствия — это строка
приёмки НФ-83, и её проверяют распаковкой пакета на чистой машине (задача Q9.13).

**Минимальная версия PostgreSQL — 15, а не 12.** ТЗ разд. 11 требует «PostgreSQL 12
и выше», и наш образ 18.6 это условие выполняет с запасом. Но накатить нашу схему
на 12-ю ветку нельзя: в `db/migrations/003_permits.sql` стоит `UNIQUE NULLS NOT
DISTINCT`, а эта конструкция появилась только в 15-й. Переписывать миграцию
не потребовалось — заказчик 19.09.2026 снял требование к стеку: «Требований
к конкретному стеку технологий нет, команды свободны в выборе инструментов» (сводный 8),
и базу на приёмке поднимает наш `docker-compose`, а не администратор заказчика.

Если разворачиваете на своей базе, а не на нашем контейнере, — она должна быть 15-й
ветки или новее. На 12, 13 и 14 накат остановится на третьей миграции. Строка
приёмки — НФ-80.

## 1. Сервер

Проверено на **6 ядрах, 11 ГБ ОЗУ, 119 ГиБ диска** — это машина заказчика.
**Настройки PostgreSQL под это железо нигде не лежат в git — их надо
накатить руками на новом стенде.** Проверила 17.09.2026: `docker-compose.yml`
не задаёт ни одного параметра `postgres`, а восемь значений на боевом
сервере (`shared_buffers` и другие) — это `postgresql.auto.conf` внутри
тома `pgdata`, файл `ALTER SYSTEM`, который живёт только в этом томе.
`docker compose down -v` стирает том целиком, значит унесёт с собой
и эти настройки, не только данные. На новом стенде под 6 ядер и 11 ГБ ОЗУ
накатить так:

```sql
ALTER SYSTEM SET shared_buffers = '3GB';
ALTER SYSTEM SET effective_cache_size = '8GB';
ALTER SYSTEM SET maintenance_work_mem = '1GB';
ALTER SYSTEM SET work_mem = '64MB';
ALTER SYSTEM SET max_wal_size = '8GB';
ALTER SYSTEM SET checkpoint_timeout = '15min';
ALTER SYSTEM SET random_page_cost = '1.1';
ALTER SYSTEM SET max_parallel_workers_per_gather = '2';
```

и перезапустить контейнер `db` (`shared_buffers` требует рестарт, не
`reload`). На машине с другой памятью и числом ядер эти восемь чисел
надо пересчитать, а не копировать — `shared_buffers` на четверть ОЗУ,
`effective_cache_size` на две трети, вот отсюда взяты 3 ГБ и 8 ГБ
для 11 ГБ этого сервера.

Место на диске уходит не на саму базу, а на пик заливки: `docs/HLD.md`
разд. 9.5 считает 50 ГБ на базу целиком плюс 22 ГБ на журнал упреждающей
записи при заливке всей истории — доля свободного места нужна с запасом
до того, как начнётся `smvu_csv.py`, а не после.

## 2. Сеть: что открыто наружу

Замерено на боевом сервере командой `ss -tlnp` 17.09.2026:

```
0.0.0.0:22    sshd           — администрирование
0.0.0.0:80    docker-proxy   — nginx, только редирект на https (deploy/nginx/nginx.conf)
0.0.0.0:443   docker-proxy   — nginx, TLS 1.2/1.3 (строка приёмки НФ-75)
127.0.0.1:5432 docker-proxy  — PostgreSQL, только с локальной машины, наружу не идёт
```

Порт 80 не отдаёт ни байта содержимого — весь `server { listen 80; }` в
`deploy/nginx/nginx.conf` состоит из одной команды `return 301 https://…`.
Контейнеры `api`, `worker` и `ml` портов наружу не публикуют вовсе —
`deploy/docker-compose.yml` не даёт им секцию `ports`, к ним можно
обратиться только через `nginx` или изнутри докер-сети.

**fail2ban не защищает 80 и 443.** Он вешает правило на входящий трафик
к самому серверу, а docker пускает трафик к опубликованным портам через
хук `forward`, мимо цепочки, которую слушает fail2ban (разбор —
`docs/server.md`, раздел про fail2ban). От перебора и флуда на 80/443
защищает `limit_req_zone` в `deploy/nginx/nginx.conf`: 30 запросов
в секунду с адреса к `/api/`, всплеск до 120; статику лимит не трогает —
её отдаёт сам nginx, до `api` и базы она не доходит. Числа сняты нагрузочным
прогоном 27.09.2026 (`docs/load-test.md`, раздел «Нагрузка») и обоснованы
в комментарии рядом с директивой.

Учётки, ключи и как зайти по SSH — `docs/server.md`, раздел «Учётки».
Здесь не повторяю: он относится к конкретному серверу, а не к процедуре
установки.

## 3. Docker: ставить из официального репозитория

**Не пакетом `docker.io` из Ubuntu.** `deploy/docker-compose.yml` написан
под `docker compose` — плагин второй версии, вызывается через пробел,
а не через дефис. В репозитории Ubuntu этот плагин лежит отдельно
и отстаёт по версии. У нас на сервере стоит Docker 29.8.0 и Compose
v5.5.1 из `https://download.docker.com/linux/ubuntu` — команды
установки и разбор, почему автозапуск после перезагрузки уже настроен
(это закрывает строку НФ-39), в `docs/server.md`, раздел «Докер стоит
с 15.09.2026».

Проверить после установки:

```
docker --version
docker compose version
docker info                # демон должен ответить, а не пожаловаться на сокет
```

## 4. Код и переменные окружения

Забрать репозиторий, дальше — три обязательных шага из `deploy/README.md`:
файл `.env` из `.env.example`, самоподписанный сертификат `make-cert.sh`,
`docker compose up -d`. Не повторяю их здесь дословно — они уже прогнаны
и описаны там с проверкой каждого шага. Два абзаца, которых в `deploy/README.md`
нет, потому что они не про сам подъём стенда, а про две находки приёмки
15.09.2026 (задача 1.6, MOS-82):

**Доступ к базе.** База читает правила доступа не из `pg_hba.conf`, который
PostgreSQL генерирует при первом старте (`initdb`), а из нашего
`deploy/db/pg_hba.conf` — его подключает строка `hba_file` в
`deploy/docker-compose.yml` (задача 1.6, MOS-82). Правил четыре:

```
local   all          all         trust
local   replication  all         trust
host    all          all   all   scram-sha-256
host    replication  all   all   scram-sha-256
```

По сокету база пускает без пароля: туда попадает только тот, у кого уже есть
шелл в контейнере `db`, то есть root над файлами данных. На этом держатся
`docker compose exec db psql` из инструкций ниже и `deploy/backup.sh`. Любой
адрес, включая `127.0.0.1` внутри самого контейнера, — только по паролю.
До 27.09.2026 действовал файл от `initdb` с `host all all 127.0.0.1/32 trust`,
и приёмка стенда 15.09.2026 зашла с паролем `неверный`. Порт 5432 по-прежнему
опубликован только на `127.0.0.1` хоста, не на `0.0.0.0`. Проверка —
`DB_CONTAINER=moskollektor-db-1 sh deploy/check-db-access.sh`: неверный пароль
на `127.0.0.1` должен получить `password authentication failed`, верный — пройти.
Отдельно ничего настраивать не нужно: файл приезжает из git и действует и на
свежей установке, и на кластере, который `initdb` завёл раньше.

**Пароль базы.** В `deploy/.env.example` пароль пустой, и compose без него
стенд не поднимет: откажется и назовёт переменную `POSTGRES_PASSWORD`. Так же
пуст `AUTH_SECRET` (ключ подписи куки входа, `openssl rand -hex 32`). До
27.09.2026 в образце стояла рабочая заглушка `СМЕНИ-МЕНЯ`, и забытый шаг
молча поднимал базу с паролем, который знает весь git (задача 1.6, MOS-82).
Генерировать настоящий пароль надо командой

```
openssl rand -hex 16
```

и вписывать в `deploy/.env`, а не в `.env.example` — этот файл в git
не идёт (`.gitignore`). На боевом сервере заглушка в `.env` не должна
остаться ни на час: 17.09.2026 проверено, что там стоит сгенерированный
пароль, а не `СМЕНИ-МЕНЯ`.

## 5. Схема, выгрузка, заглушка модели, интерфейс

Порядок и точные команды — `deploy/README.md`, разделы «Накатить схему»,
«Залить выгрузку СМВУ», «Поднять заглушку модели», «Поднять API и выложить
интерфейс». Заливка выгрузки идёт на самом сервере, а не с машины
разработчика — раздел «Где заливать» в `deploy/README.md` объясняет,
почему на маке не хватает места на седьмом файле из восьми.

После заливки выгрузки прогоните `migrate` ещё раз: демо прогноза по датчикам
(`/map?demo=sensors`) берёт синтетический паспорт оборудования из сида, а сид
пишет его только на уже залитые каналы — абзац «Синтетика по датчикам появляется при втором накате»
в `deploy/README.md`.

Собранный интерфейс кладётся в `deploy/nginx/app`, а не в `deploy/nginx/html`.
В `html` лежит заглушка «Стенд поднят», nginx отдаёт её, только пока `app` пуст.
Если после выкладки в корне стенда по-прежнему «Стенд поднят», фронт не собран
или лежит не там; проверка — строка «М-03 стенд отдаёт приложение»
в `delivery/check-all.sh`.

## 6. Резервные копии

Копии идут сами, отдельной настройки не нужно. `docker compose up -d` поднимает
вместе с базой контейнер `backup`: он раз в сутки в 02:00 по Москве снимает копию
кластера в том `backups` и хранит последнюю, а база между копиями сама кладёт
туда же архив журнала — не реже раза в 15 минут. Время и число копий задают
`BACKUP_AT` и `BACKUP_KEEP` в `deploy/.env`. Одна копия — по месту на нашем стенде;
сколько копий помещается на вашем диске, через сутки работы покажет
`DB_CONTAINER=moskollektor-db-1 sh deploy/wal-rate.sh 60` (`docs/restore.md`,
«Сколько хранить»).

Проверить, что копии идут:

```
DB_CONTAINER=moskollektor-db-1 sh deploy/check-backup.sh
```

Как восстановиться после аварии, как провести учения восстановления, не трогая
живую базу, и сколько это занимает по времени — `docs/restore.md`.

**Одна оговорка.** Том `backups` лежит на том же диске, что и база: отказ диска
целиком унесёт и то и другое. Каталог тома на хосте показывает
`docker volume inspect moskollektor_backups`, и его надо уносить на отдельное
хранилище средствами эксплуатации.

## 7. Убедиться, что всё поднялось

`docker compose up -d` возвращает код 0, даже когда обе службы упали
сразу после старта — подробный разбор и все команды проверки живости
(`docker compose ps`, curl по 127.0.0.1 и `[::1]`, `pg_isready`) —
`deploy/README.md`, раздел «Убедиться, что поднялось». Замер TLS для
приёмки (строка НФ-75) — тот же файл, раздел «Замер TLS для приёмки».

## 8. Проверки на приёмке: чем мы доказываем числа

Комиссии мало нашего слова, что Precision такой-то. Поэтому приёмочные проверки
лежат внутри образа `api`, и запустить их может любой, у кого поднят стенд.
Это строка приёмки НФ-03 и задача `MOS-120`.

Запускать надо **внутри контейнера**, а не на хосте: `DATABASE_URL` там уже задан,
и база видна по имени `db`.

```
# метрики М-18…М-21: Precision, Recall, упреждение, время расчёта
docker compose exec api python code/check_metrics.py

# программа минимум, 21 строка М-01…М-21
docker compose exec api python code/check_minimum.py

# схема базы: порядок миграций и целостность
docker compose exec api python code/check_schema.py

# постраничность GET /api/forecasts (НФ-88)
docker compose exec api python code/check_api_paging.py

# блокировка расчёта: два экземпляра не считают одно и то же
docker compose exec api python code/check_lock.py
```

Каждый скрипт **по умолчанию отказывает**, а не соглашается: без `DATABASE_URL`
он печатает `СБОЙ` и выходит с ненулевым кодом. Зелёный ответ означает, что
проверка действительно прошла, а не что она не нашла, к чему придраться.

**Какие проверки где запускать — 28.09.2026, MOS-156.** Проверок в `code/` 38, и они
делятся на две группы по тому, что им нужно. Кто запустит проверку не в том месте,
получит не трассировку, а отказ со словами «задайте DATABASE_URL» или «нет каталога»;
до правки 21 из 38 падали в образе трассировкой `ModuleNotFoundError` или
`FileNotFoundError` на исправном продукте.

*В контейнере `api` — 27 проверок, им нужна база или стенд.* `backend/Dockerfile`
ставит `PYTHONPATH=/app`, поэтому они видят код `app.*` без подсказок:
`check_api_paging`, `check_auth`, `check_block_user`, `check_card_weight`,
`check_explain_templates`, `check_frontend`, `check_ingest`, `check_lock`,
`check_metrics`, `check_metrics_report`, `check_migration_hashes`, `check_minimum`, `check_model_and_objects`,
`check_order_status`, `check_orders`, `check_risk_deadzone`, `check_runtime`,
`check_schema`, `check_section_xref`, `check_seed_rbac`, `check_spread`,
`check_stable_paging`, `check_stream`, `check_tech_events`, `check_trust_header`,
`check_weather`, `check_xml_response`. Запуск: `docker compose exec api python code/<имя>.py`.

*Из распакованного пакета — 11 проверок, им нужны файлы репозитория* (`docs/`,
`frontend/src`, исходники `backend/app`). В образ их не пускает `.dockerignore`, чтобы
комиссия не нашла там проверку, которая заведомо упадёт:
`check_contrast`, `check_dependency_pins`, `check_deploy_set`, `check_licenses`,
`check_no_auto_verdict`, `check_pg_version`, `check_plan`,
`check_stale_fetch`, `check_structure`, `check_unmet`, `check_write_policy`. Запуск из
корня пакета: `python3 code/<имя>.py`. `check_metrics_report` лежит в обоих местах:
в образе он нужен как модуль (`check_orders` берёт из него окно замера), а сам отчёт
и доказательства проверяет только из пакета — в контейнере он скажет это словами; все разом с привязкой к строкам приёмки —
`bash delivery/check-all.sh`. `check_structure` — исключение: она сверяет счётчики каталогов с `git ls-tree`, поэтому работает только из клона репозитория, а не из архива `delivery/pack.sh`, где `.git` нет.

`check_licenses` сверяет перечень `docs/libraries.md` с `node_modules`, а в них
платформенные сборки (`@rolldown/binding-darwin-arm64` на Маке, `-linux-x64-gnu`
на Linux). Перечень составлен на Маке, поэтому на Linux проверка печатает
расхождение по этим пакетам — пакеты другие, лицензии у них те же.

**Третья не живёт в образе и жить не может — `delivery/check-a11y.mjs`.** Она водит
настоящий браузер: поднимает Chrome, нажимает Tab и Enter и читает дерево доступности,
из которого программа чтения с экрана строит речь для незрячего диспетчера. Образ `api`
собран из `python:3.14-slim`, ни Node, ни Chrome там нет, и класть их туда ради одной
проверки — это сотни мегабайт к образу. Поэтому её запускают с машины приёмщика,
из распакованного пакета:

```
BASE_URL=https://135.106.216.101 BUNDLE=stand node delivery/check-a11y.mjs
```

Нужны Node 22 и выше — в нём `WebSocket` уже лежит в стандартной поставке, и проверка
не ставит ни одного пакета, — и установленный Chrome. Путь к Chrome задаётся переменной
`CHROME`, по умолчанию берётся путь macOS. Без Node или без Chrome проверка называет,
чего не хватает, и выходит с ненулевым кодом, а не молчит.

**Переменная `BUNDLE=stand` обязательна.** В этом режиме браузер исполняет бандл,
лежащий на стенде. Без неё проверка смотрит локальную сборку `frontend/dist` и закроет
строку НФ-92 на коде, которого заказчику не отдавали: 22.09.2026 локальный прогон
в ту же минуту давал «проблем нет», а стендовый — «сбоев 9».

**Почему проверки вообще внутри образа.** До 21.09.2026 каталог `code/` целиком стоял
в `.dockerignore`, и на стенде заказчика доказывать метрики было бы нечем — скрипт,
которым мы их меряем, в поставку не попадал. Сейчас в игноре стоит `code/*` с двумя
исключениями: `!code/check_*.py` и `!code/predictive_metrics.py`. Прототипы и
разведочные скрипты по-прежнему остаются снаружи.
