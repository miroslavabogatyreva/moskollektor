# Как развернуть стенд с нуля

Инструкция для человека, у которого есть только чистая машина Debian/Ubuntu
и доступ по SSH — ни Docker, ни репозитория, ни `.env` на ней ещё нет. Она
охватывает то, чего нет в `deploy/README.md`: саму машину, сеть вокруг неё
и резервные копии. Три шага docker compose — TLS, пароль базы, `up -d` —
подробно разобраны в `deploy/README.md`, здесь на них только ссылка, чтобы
не держать одно и то же в двух файлах. Проверено на сервере заказчика
`135.106.216.101`, Ubuntu 24.04.4 LTS — факты и учётки того сервера
в `docs/server.md`.

## 0. Что именно разворачивается и на какой версии базы

**Развёртывать эту систему будем не мы.** 19.09.2026 заказчик написал: «Формат сдачи -
это пакет, который можно распаковать и запустить, с обязательной инструкцией
по развертыванию», и отдельно — «организаторы будут разворачивать на своих мощностях
для оценки» (`docs/meetings/2026-09-19-ответы-заказчика.md`, сводные 18 и 10). Значит
инструкция читается человеком, который наш репозиторий видит впервые и спросить у нас
не может. Всё, что в ней описано, должно работать без нашего присутствия — это строка
приёмки НФ-83, и её проверяют распаковкой пакета на чистой машине (задача Q9.13).

**Минимальная версия PostgreSQL — 15, а не 12.** ТЗ разд. 11 требует «PostgreSQL 12
и выше», и наш образ 18.6 это условие выполняет с запасом. Но накатить нашу схему
на 12-ю ветку нельзя: в `db/migrations/003_permits.sql` стоит `UNIQUE NULLS NOT
DISTINCT`, а эта конструкция появилась только в 15-й. Переписывать миграцию
не потребовалось — заказчик 19.09.2026 снял требование к стеку: «Требований
к конкретному стеку технологий нет, команды свободны в выборе инструментов» (сводный 8),
и базу на приёмке поднимает наш `docker-compose`, а не администратор заказчика.

Если разворачиваете на своей базе, а не на нашем контейнере, — она должна быть 15-й
ветки или новее. На 12, 13 и 14 накат остановится на третьей миграции. Строка
приёмки — НФ-80.

## 1. Сервер

Проверено на **6 ядрах, 11 ГБ ОЗУ, 119 ГиБ диска** — это машина заказчика.
**Настройки PostgreSQL под это железо нигде не лежат в git — их надо
накатить руками на новом стенде.** Проверила 17.09.2026: `docker-compose.yml`
не задаёт ни одного параметра `postgres`, а восемь значений на боевом
сервере (`shared_buffers` и другие) — это `postgresql.auto.conf` внутри
тома `pgdata`, файл `ALTER SYSTEM`, который живёт только в этом томе.
`docker compose down -v` стирает том целиком, значит унесёт с собой
и эти настройки, не только данные. На новом стенде под 6 ядер и 11 ГБ ОЗУ
накатить так:

```sql
ALTER SYSTEM SET shared_buffers = '3GB';
ALTER SYSTEM SET effective_cache_size = '8GB';
ALTER SYSTEM SET maintenance_work_mem = '1GB';
ALTER SYSTEM SET work_mem = '64MB';
ALTER SYSTEM SET max_wal_size = '8GB';
ALTER SYSTEM SET checkpoint_timeout = '15min';
ALTER SYSTEM SET random_page_cost = '1.1';
ALTER SYSTEM SET max_parallel_workers_per_gather = '2';
```

и перезапустить контейнер `db` (`shared_buffers` требует рестарт, не
`reload`). На машине с другой памятью и числом ядер эти восемь чисел
надо пересчитать, а не копировать — `shared_buffers` на четверть ОЗУ,
`effective_cache_size` на две трети, вот отсюда взяты 3 ГБ и 8 ГБ
для 11 ГБ этого сервера.

Место на диске уходит не на саму базу, а на пик заливки: `docs/HLD.md`
разд. 9.5 считает 50 ГБ на базу целиком плюс 22 ГБ на журнал упреждающей
записи при заливке всей истории — доля свободного места нужна с запасом
до того, как начнётся `smvu_csv.py`, а не после.

## 2. Сеть: что открыто наружу

Замерено на боевом сервере командой `ss -tlnp` 17.09.2026:

```
0.0.0.0:22    sshd           — администрирование
0.0.0.0:80    docker-proxy   — nginx, только редирект на https (deploy/nginx/nginx.conf)
0.0.0.0:443   docker-proxy   — nginx, TLS 1.2/1.3 (строка приёмки НФ-75)
127.0.0.1:5432 docker-proxy  — PostgreSQL, только с локальной машины, наружу не идёт
```

Порт 80 не отдаёт ни байта содержимого — весь `server { listen 80; }` в
`deploy/nginx/nginx.conf` состоит из одной команды `return 301 https://…`.
Контейнеры `api`, `worker` и `ml` портов наружу не публикуют вовсе —
`deploy/docker-compose.yml` не даёт им секцию `ports`, к ним можно
обратиться только через `nginx` или изнутри докер-сети.

**fail2ban не защищает 80 и 443.** Он вешает правило на входящий трафик
к самому серверу, а docker пускает трафик к опубликованным портам через
хук `forward`, мимо цепочки, которую слушает fail2ban (разбор —
`docs/server.md`, раздел про fail2ban). От перебора и флуда на 80/443
защищает `limit_req_zone` в `deploy/nginx/nginx.conf`: 30 запросов
в секунду с адреса, всплеск до 60 — числа обоснованы в комментарии
рядом с директивой.

Учётки, ключи и как зайти по SSH — `docs/server.md`, раздел «Учётки».
Здесь не повторяю: он относится к конкретному серверу, а не к процедуре
установки.

## 3. Docker: ставить из официального репозитория

**Не пакетом `docker.io` из Ubuntu.** `deploy/docker-compose.yml` написан
под `docker compose` — плагин второй версии, вызывается через пробел,
а не через дефис. В репозитории Ubuntu этот плагин лежит отдельно
и отстаёт по версии. У нас на сервере стоит Docker 29.8.0 и Compose
v5.5.1 из `https://download.docker.com/linux/ubuntu` — команды
установки и разбор, почему автозапуск после перезагрузки уже настроен
(это закрывает строку НФ-39), в `docs/server.md`, раздел «Докер стоит
с 15.09.2026».

Проверить после установки:

```
docker --version
docker compose version
docker info                # демон должен ответить, а не пожаловаться на сокет
```

## 4. Код и переменные окружения

Забрать репозиторий, дальше — три обязательных шага из `deploy/README.md`:
файл `.env` из `.env.example`, самоподписанный сертификат `make-cert.sh`,
`docker compose up -d`. Не повторяю их здесь дословно — они уже прогнаны
и описаны там с проверкой каждого шага. Два абзаца, которых в `deploy/README.md`
нет, потому что они не про сам подъём стенда, а про две находки приёмки
15.09.2026 (задача 1.6, MOS-82):

**Доступ к базе.** `pg_hba.conf`, который PostgreSQL генерирует при первом
старте (`initdb`), содержит:

```
local   all   all                trust
host    all   all   127.0.0.1/32 trust
host    all   all   ::1/128      trust
host    all   all   all          scram-sha-256
```

Внутри контейнера это значит: с loopback-адреса база пускает с любым
паролем — проверила приёмка стенда 15.09.2026, зашли с паролем `неверный`
(задача 1.6, MOS-82); правило на месте и сегодня, я перечитала файл на
сервере 17.09.2026. Наружу дыры нет по трём
причинам разом: порт 5432 в `deploy/docker-compose.yml` опубликован
только на `127.0.0.1` хоста (не `0.0.0.0`), сам хост — не рабочее место
диспетчера, а с любого другого адреса, включая другой контейнер докер-сети,
последняя строка требует `scram-sha-256` и заглушку не пропустит. Правило
`trust` на loopback — это как раз то, что позволяет `docker compose exec
db psql` из инструкций ниже работать без пароля в командной строке.
На приёмке по Регламенту про доступ к базе спросят — этот абзац и есть
ответ, отдельно ничего не настраивать не нужно.

**Пароль базы.** Заглушка `POSTGRES_PASSWORD=СМЕНИ-МЕНЯ` в
`deploy/.env.example` рабочая: если её не заменить, стенд поднимется
и будет отвечать. Генерировать настоящий пароль надо командой

```
openssl rand -hex 16
```

и вписывать в `deploy/.env`, а не в `.env.example` — этот файл в git
не идёт (`.gitignore`). На боевом сервере заглушка в `.env` не должна
остаться ни на час: 17.09.2026 проверено, что там стоит сгенерированный
пароль, а не `СМЕНИ-МЕНЯ`.

## 6. Резервные копии — их пока нет

**Честно: задачи Q1.2 и Q1.9 не сделаны.** В `deploy/docker-compose.yml`
объявлен том `backups`, смонтированный в контейнер `db` на `/backups`,
но ни скрипта, ни расписания, которое туда что-то кладёт, не существует —
на сервере `crontab -l` для `root` пуст, а `deploy/backup.sh` в репозитории
нет. Том — это место под будущий бэкап, а не сам бэкап.

Целевые показатели уже посчитаны и ждут реализации — `docs/HLD.md`
разд. 9.2: RPO 1 час (журналы БД каждые 15 минут), RTO 4 часа,
ежедневный дифференциальный дамп плюс полный раз в неделю, отдельно —
бессрочный архив исходных выгрузок СМВУ после каждой загрузки. Пока
это проектная цель, а не работающий механизм: единственная копия данных
сегодня — сама база в томе `pgdata`, и `docker compose down -v` сотрёт
её без возврата.

## 8. Проверки на приёмке: чем мы доказываем числа

Комиссии мало нашего слова, что Precision такой-то. Поэтому приёмочные проверки
лежат внутри образа `api`, и запустить их может любой, у кого поднят стенд.
Это строка приёмки НФ-03 и задача `MOS-120`.

Запускать надо **внутри контейнера**, а не на хосте: `DATABASE_URL` там уже задан,
и база видна по имени `db`.

```
# метрики М-18…М-21: Precision, Recall, упреждение, время расчёта
docker compose exec api python code/check_metrics.py

# программа минимум, 21 строка М-01…М-21
docker compose exec api python code/check_minimum.py

# схема базы: порядок миграций и целостность
docker compose exec api python code/check_schema.py

# постраничность GET /api/forecasts (НФ-88)
docker compose exec api python code/check_api_paging.py

# блокировка расчёта: два экземпляра не считают одно и то же
docker compose exec api python code/check_lock.py
```

Каждый скрипт **по умолчанию отказывает**, а не соглашается: без `DATABASE_URL`
он печатает `СБОЙ` и выходит с ненулевым кодом. Зелёный ответ означает, что
проверка действительно прошла, а не что она не нашла, к чему придраться.

Две проверки в контейнере работать не будут, и это ожидаемо: `check_licenses.py`
и `check_model_and_objects.py` читают файлы из `docs/`, а документы в образ не едут.
Их запускают из распакованного пакета поставки, где `docs/` лежит рядом.

**Почему проверки вообще внутри образа.** До 21.09.2026 каталог `code/` целиком стоял
в `.dockerignore`, и на стенде заказчика доказывать метрики было бы нечем — скрипт,
которым мы их меряем, в поставку не попадал. Сейчас в игноре стоит `code/*` с двумя
исключениями: `!code/check_*.py` и `!code/predictive_metrics.py`. Прототипы и
разведочные скрипты по-прежнему остаются снаружи.
