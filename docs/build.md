# Как собрать образы

Четыре части поставки, а собираем мы только две: образ `api`/`worker` (один
Dockerfile на оба) и образ `ml`-заглушки. `nginx` — готовый образ, берём как
есть. Фронт — не образ вовсе, а статика, собранная локально и скопированная
на сервер. Все команды ниже прогнаны 17.09.2026: `api` и `ml-stub` —
локально (`docker build`), фронт — локально (`npm run build`), проверка
свежести выкладки — на сервере заказчика по SSH, без пересборки (на стенде
сейчас работают другие сессии, пересобирать там не буду).

## 1. Базовые образы — версии из `docs/HLD.md` разд. 7.1.1

Сверены на Docker Hub 14.09.2026, не по памяти:

| Контейнер | Базовый образ | Вес готового образа (сервер, `linux/amd64`) |
|---|---|---|
| `api`, `worker`, `migrate` | `python:3.14-slim` | 247 МБ, 247 МБ, 245 МБ |
| `ml` (заглушка) | `python:3.14-slim` | 227 МБ |
| `nginx` | `nginx:1.31-alpine`, готовый, не собираем | 103 МБ |
| `db` | `postgis/postgis:18-3.6`, готовый, не собираем | 957 МБ |

Замер сделан на сервере (`docker images`, 17.09.2026): один `python:3.14-slim`
собирает три разных контейнера — `api`, `worker` и `migrate` отличаются только
командой запуска в `deploy/docker-compose.yml`, а код у них общий процентов
на восемьдесят, как записано в `docs/HLD.md` разд. 7.1. Локальная сборка
на маке (Apple Silicon, без `--platform`) даёт 272 МБ для `api` и 252 МБ
для `ml-stub` — вес отличается от сервера архитектурой слоёв, а не составом,
для сдачи считается вес на `linux/amd64`, потому что там будет жить продукт.

Фронт собирается не в контейнере: `frontend/Dockerfile` в репозитории нет,
и `node:24-alpine` из таблицы разд. 7.1.1 сегодня нигде не используется —
он останется базовым образом стадии сборки фронта, когда такая стадия
появится, а сейчас `npm run build` идёт на машине разработчика (раздел 3).

## 2. Сборка `api`/`worker`/`migrate`

Один Dockerfile на все три, контекст сборки — корень репозитория (не `backend/`):
образ вшивает `db/migrations/`, `db/seed/` и `contracts/`, а не только код `app/`.

```
docker build -t moskollektor-api -f backend/Dockerfile .
```

Через `docker compose` то же самое делает `--profile app build api` (или
`worker`, или `migrate`) из каталога `deploy` — оба пути собирают один
и тот же `backend/Dockerfile`. Прогнано локально 17.09.2026: сборка с нуля
(без кэша слоёв) заняла меньше минуты, `pip install` не компилирует ничего
из исходников — под `cp314` есть готовые колёса и на `asyncpg`, и на `duckdb`
(обоснование выбора версии Python — `docs/HLD.md` разд. 7.1.1).

**Правка любого файла в `db/migrations/` требует пересборки образа.**
Миграции скопированы внутрь (`COPY db/migrations ./db/migrations`), а не
примонтированы томом: `backend/app/migrate.py` сверяет sha256 файла внутри
контейнера со значением в `public.schema_migration`, и без пересборки
внутри останется старое содержимое.

**Правка файла в `db/seed/` требует пересборки образа по той же причине.**
Сиды контейнер `migrate` накатывает после миграций, и в образ они входят строкой
`COPY db/seed ./db/seed` рядом с `COPY db/migrations ./db/migrations`. Без
пересборки `migrate` возьмёт старый файл из образа: журнал
`public.schema_migration` сиды не записывает, сверять их не с чем.

## 3. Сборка `ml` (заглушка)

Пока Николай не прислал образ модели (задача Q7.3, контракт — `docs/HLD.md`
разд. 6), на его месте заглушка. Контекст сборки — тоже корень репозитория,
потому что в образ едет `contracts/`: без него самопроверка заглушки не
сверится с примерами сообщений.

```
docker build -t moskollektor/ml-stub:latest -f ml-stub/Dockerfile .
```

Собирается за секунды: слоёв мало, зависимость только `uvicorn`. Подмена
на настоящий образ — правка `ML_IMAGE` в `deploy/.env`, ни одна строка
кода при этом не меняется (`ml-stub/Dockerfile`, первая строчка комментария).

## 4. Сборка фронта

```
cd frontend
npm ci                # не npm install — в репозитории есть package-lock.json
npm run build          # tsc --noEmit, потом vite build
```

Замер 17.09.2026 (`vite build`, 26 модулей, 142 мс):

```
dist/assets/index-*.js    45,05 КБ, gzip 14,13 КБ
dist/assets/index-*.css   11,18 КБ, gzip  3,36 КБ
```

**Бюджет проверяем не по числу vite, а отдельной командой** — она и есть
контрольная для сдачи (`docs/HLD.md` разд. 4.1, бюджет 150 КБ на весь
сжатый JS):

```
gzip -c dist/assets/*.js | wc -c    # 13954 — меньше 153600 (150×1024), запас есть
```

Разница между 14,13 КБ у vite и 13 954 Б (≈13,63 КБ) здесь — это разные
уровни сжатия gzip у двух инструментов, а не два разных бандла; для приёмки
годится только вторая цифра, потому что это ровно та команда, которой
меряют бюджет в `docs/HLD.md`.

Стек — Vite + Preact + TypeScript + Tailwind, не Next.js: обоснование
числом (107 КБ у пустой заготовки Next.js против бюджета 150 КБ на всё)
в `docs/HLD.md` вводной и разд. 4.1, здесь не повторяю.

**Собранное — файлы, не контейнер.** `frontend/dist/` копируется на сервер
`rsync`-ом в каталог `deploy/nginx/app`, который `nginx` монтирует на `/usr/share/nginx/app`
(`deploy/README.md`, раздел «Интерфейс — это статика, а не контейнер»).
Пересобрать и не выложить — самая частая ошибка: без обоих шагов подряд
стенд показывает вчерашний интерфейс.

## 5. Проверить, что на сервере лежит именно новая сборка

`rsync` переносит время файла с машины-источника, поэтому `ls -l` на
сервере показывает возраст правки, а не возраст выкладки. Доказательство —
содержимым, а не датой (`docs/server.md`, «Как выкладывать код и что при
этом ломается»):

```
docker exec moskollektor-nginx-1 grep -c "<строка-метка из новой правки>" \
    /usr/share/nginx/app/assets/index-*.js
```

Ноль совпадений — старая сборка не заменилась; если файл лежит внутри
смонтированного тома (не статика фронта, а конфиг вроде `nginx.conf`),
`nginx -s reload` может отработать на СТАРОМ содержимом молча — том
привязан по inode, а `rsync` пишет через переименование. В этом случае
нужен `docker compose restart nginx`, а не `reload`.

## 6. Ловушка: `docker compose up -d` не проверяет, что внутри живо

Команда возвращает код 0, даже когда обе службы упали сразу после
старта, — она сообщает, что контейнеры созданы и запущены, а не что
процессы внутри работают. После пересборки и подъёма всегда

```
docker compose ps    # ждём (healthy) у каждой службы с healthcheck
```

а не полагаемся на код выхода команды. Полный разбор и команды проверки
живости через curl — `deploy/README.md`, раздел «Убедиться, что поднялось».
