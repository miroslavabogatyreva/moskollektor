или настраиваете доступ. Правила работы над проектом — в `CLAUDE.md`.

Сервер `135.106.216.101`, hostname `moskollektor`, Ubuntu 24.04.4 LTS.

## Учётки

- **`root`** — у Мирославы, вход по ключу.
- **`nikolay-hakaton`** — у Николая, я завела её 15.09.2026. Николай подключается
  командой `ssh nikolay-hakaton@135.106.216.101`, его публичный ключ лежит
  в `/home/nikolay-hakaton/.ssh/authorized_keys`. Пароль на учётке я заблокировала
  (`passwd -l`), так что вход только по ключу. `sudo` работает без пароля —
  правило `nikolay-hakaton ALL=(ALL) NOPASSWD:ALL` я положила
  в `/etc/sudoers.d/nikolay-hakaton` 15.09.2026. Там же 15.09.2026 я добавила его
  в группу `docker` (`usermod -aG docker nikolay-hakaton`), чтобы он запускал
  контейнеры без `sudo`: `id nikolay-hakaton` показывает
  `groups=1000(nikolay-hakaton),27(sudo),989(docker)`. Новых прав это ему не дало —
  полный root у него и так был по правилу `NOPASSWD:ALL` строкой выше; членство
  в группе только убирает `sudo` перед каждой командой.

## Докер стоит с 15.09.2026

До этого дня на сервере не было ни движка, ни плагина: `dpkg -l | grep -iE 'docker|containerd'`
не давал ни строки. Поставили из официального репозитория Docker, а не пакетом `docker.io`
из Ubuntu: наш `deploy/docker-compose.yml` написан под `docker compose` второй версии,
а в репозитории Ubuntu плагин лежит отдельно и отстаёт по версии.

```
docker --version        -> Docker version 29.8.0, build 88096ef
docker compose version  -> Docker Compose version v5.5.1
systemctl is-enabled docker -> enabled
systemctl is-active  docker -> active
```

Автозапуск после перезагрузки есть: apt создал симлинки на `docker.service`,
`docker.socket` и `containerd.service` в `multi-user.target.wants`. Это нужно строке
приёмки НФ-39 — стенд, который не встаёт сам, восстановление за 4 часа не закроет.

Установка съела 1,54 ГиБ вместе с образами `hello-world` и `postgis/postgis:18-3.6`.
На диске было занято 16 ГиБ из 119, стало 18 ГиБ, свободно 96 ГиБ. Вычесть 16 ГиБ
выгрузки в `/srv` — под базу с журналом СМВУ на 313 546 016 строк остаётся около
80 ГиБ, и это до места под WAL и индексы, которое при заливке уходит быстрее,
чем под сами строки.

Образ базы проверен на месте: `docker run --rm postgis/postgis:18-3.6 postgres --version`
отвечает `postgres (PostgreSQL) 18.6 (Debian 18.6-1.pgdg13+2)`, а PostGIS в нём 3.6.4.
Архитектура сервера `x86_64` — для этого образа родная, эмуляции нет.

## Стенд и база живут здесь, а не на машине разработчика

**Решено 15.09.2026, и вот почему.** Сначала я залила выгрузку в докер на маке.
База выросла до 35 ГБ при 66 ГБ свободных, место кончилось на седьмом файле из восьми,
и три индекса строить стало негде. На сервере свободно 96 ГБ из 119, а сама выгрузка
уже лежит здесь — по сети не гоняется ничего. Заливку пришлось начинать заново.

Что стоит на сервере после этого:

```
/srv/moskollektor/          db, backend, deploy, contracts, ml-stub — без .git и dataset
/srv/moskollektor/deploy/.env   пароль базы, в репозиторий не идёт
/srv/moskollektor/.venv/    python 3.12 плюс asyncpg, для запуска загрузчика
/srv/moskollektor/load-*.log    журналы заливки по потокам
```

Настройки базы выставлены под это железо (6 ядер, 11 ГБ), а не по умолчанию:
`shared_buffers = 3GB`, `maintenance_work_mem = 1GB`, `max_wal_size = 8GB`,
`effective_cache_size = 8GB`. На маке под кэш было 128 МБ, и это половина тормозов.

Подключиться к базе со стенда:

```
docker exec moskollektor-db-1 psql -U moskollektor -d moskollektor -c "SELECT count(*) FROM smvu.reading"
```

**Ловушка, на которой я потеряла два захода.** В `bash` на этом сервере не работают
кириллические имена переменных: `СЛОТ=1` отвечает `command not found`, подстановка
даёт пустую строку, и команда молча запускается не с теми параметрами. В скриптах
для сервера имена переменных только латиницей. Вторая ловушка того же рода:
`docker compose exec -T` читает стандартный ввод и съедает остаток скрипта,
переданного через `ssh bash -s` — закрывайте ввод явно, `< /dev/null`.

## Вход по паролю отключён для всех учёток

Я выключила его 15.09.2026, и на это ушло время: `PasswordAuthentication` упорно
оставался в `yes`, хотя в основном `sshd_config` стояло `no`. Причина — файл
`/etc/ssh/sshd_config.d/50-cloud-init.conf`: cloud-init подключается раньше основного
конфига и перебивает его. Правили именно файл cloud-init.

Проверить, что получилось на самом деле, можно только так — команда на сервере:

```
sshd -T | grep passwordauthentication
```

Она печатает эффективное значение, то есть то, с которым демон реально работает,
а не то, что написано в каком-то одном файле.

## fail2ban: баним перебор ключей по ssh

Поставила 15.09.2026, пакет `fail2ban` из репозитория Ubuntu, версия 1.0.2.
Повод простой: за сутки до установки в журнале лежало 702 строки неудачных входов,
это чужие сканеры перебирают имена вроде `admin` и `root`. Пароль на вход отключён,
подобрать они ничего не могут, но журнал засоряют и нагрузку дают.

Параметры я положила в `/etc/fail2ban/jail.local` — этот файл перекрывает `jail.conf`
и переживает обновление пакета. Бан на час, пять попыток за десять минут,
`ignoreip = 127.0.0.1/8 ::1`. Час, а не «навсегда», выбран нарочно: если кто-то из нас
упрётся в бан по своей ошибке, он снимется сам, без похода в консоль хостера.

**Одна строка в этом файле обязательна, без неё fail2ban работает вхолостую.**
Фильтр `/etc/fail2ban/filter.d/sshd.conf` ищет в журнале записи юнита `sshd.service`,
а в Ubuntu 24.04 юнит называется `ssh.service`. Разница видна сразу:

```
journalctl _SYSTEMD_UNIT=ssh.service  --since '24 hours ago' | wc -l   # 890
journalctl _SYSTEMD_UNIT=sshd.service --since '24 hours ago' | wc -l   # 1
```

Пока я не дописала в секцию `[sshd]` строку

```
journalmatch = _SYSTEMD_UNIT=ssh.service + _COMM=sshd
```

`fail2ban-client status sshd` показывал живой jail и `Total failed: 0` при семистах
неудачных входах в сутки. То есть служба выглядела рабочей и не ловила ничего.

Проверила двумя способами. Первый — прогнала фильтр по настоящему журналу:

```
fail2ban-regex systemd-journal /etc/fail2ban/filter.d/sshd.conf \
  --journalmatch "_SYSTEMD_UNIT=ssh.service + _COMM=sshd"
```

Он ответил `Failregex: 788 total`, `Lines: 922 lines, 483 ignored, 305 matched`.
Второй — сделала шесть заведомо неудачных входов несуществующим пользователем
с самого сервера на его же адрес. `Total failed` стал 12, `Total banned` — 1,
в списке забаненных появился `135.106.216.101`, а в nftables — правило
`tcp dport 22 ip saddr @addr-set-sshd reject with icmp port-unreachable`.
Тестовый бан я сняла сразу: `fail2ban-client set sshd unbanip 135.106.216.101`.

Служба поднимается после перезагрузки: `systemctl is-enabled fail2ban` отвечает
`enabled`. Места заняла 11 МБ.

**Чего fail2ban у нас не закрывает.** Он вешает правило на входящий трафик к самому
серверу, а докер пускает трафик к опубликованным портам контейнеров мимо этой цепочки.
Значит порты, которые мы откроем наружу для API и карты, fail2ban не защитит — когда
дойдём до публикации стенда, защиту от перебора надо будет ставить отдельно,
на уровне nginx.
