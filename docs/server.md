## Домен и сертификат

С 27.09.2026 стенд открывается по имени **https://moskollektor.mbogatyreva.ru**.

**DNS.** В Cloudflare, в зоне `mbogatyreva.ru`, я завела запись
`A moskollektor → 135.106.216.101`. Проксирование Cloudflare (оранжевое облако)
я не включала, запись работает только как DNS. Причин три. Cloudflare обрывает
запрос через 100 секунд ошибкой 524, а экран журнала у нас уже отвечал 112 секунд.
Российские провайдеры замедляют Cloudflare. И TLS должен отдавать наш nginx,
иначе протоколы `docs/protocol-tls-*.md` перестанут описывать то, что видит клиент.

**Сертификат.** Его выпускает Let's Encrypt через `certbot certonly --standalone`
прямо на сервере, срок 90 дней, первый действует до 26.12.2026. Nginx стенда читает
`deploy/nginx/certs/server.crt` и `server.key`. Имена файлов я сохранила, поэтому
`nginx.conf` и compose не менялись.

**Продление** делает `certbot.timer` дважды в сутки. Порт 80 занят нашим nginx, и
certbot освобождает его сам: команда `docker compose -f /srv/moskollektor/deploy/docker-compose.yml stop nginx`
из `pre_hook` останавливает nginx секунд на десять. Потом хук
`/etc/letsencrypt/renewal-hooks/deploy/moskollektor.sh` копирует `fullchain.pem`
и `privkey.pem` в `deploy/nginx/certs/`, а команда `start nginx` из `post_hook` поднимает nginx.
Хуки лежат в `/etc/letsencrypt/renewal/moskollektor.mbogatyreva.ru.conf`.
Проверка продления: `certbot renew --dry-run` должен напечатать `(success)`.
Этот хук срабатывает только при продлении. После первого выпуска я запустила его руками:
`RENEWED_LINEAGE=/etc/letsencrypt/live/moskollektor.mbogatyreva.ru /etc/letsencrypt/renewal-hooks/deploy/moskollektor.sh`.

**Откат.** Самоподписанный сертификат лежит рядом, в `server.crt.selfsigned.bak`
и `server.key.selfsigned.bak`. `deploy.sh` каталог `certs/` не трогает, в git он
не идёт. Затереть сертификат может только ручной запуск `sh deploy/make-cert.sh`,
и то до ближайшего продления.

## Стенд и база живут здесь, а не на машине разработчика

**Решено 15.09.2026, и вот почему.** Сначала я залила выгрузку в докер на маке.
База выросла до 35 ГБ при 66 ГБ свободных, место кончилось на седьмом файле из восьми,
и три индекса строить стало негде. На сервере свободно 96 ГБ из 119, а сама выгрузка
уже лежит здесь — по сети не гоняется ничего. Заливку пришлось начинать заново.

Что стоит на сервере после этого:

```
/srv/moskollektor/          git-копия origin/master (с 27.09.2026), без dataset
/srv/moskollektor/deploy/.env   пароль базы, в репозиторий не идёт
/srv/moskollektor/.venv/    python 3.12 плюс asyncpg, для запуска загрузчика
/srv/moskollektor/load-*.log    журналы заливки по потокам
```

Настройки базы выставлены под это железо (6 ядер, 11 ГБ), а не по умолчанию:
`shared_buffers = 3GB`, `maintenance_work_mem = 1GB`, `max_wal_size = 8GB`,
`effective_cache_size = 8GB`. На маке под кэш было 128 МБ, и это половина тормозов.

**`/dev/shm` контейнера `db` — 1 ГиБ (MOS-222, Q1.17), добавлено 23.09.2026.**
Докеровское умолчание — 64 МБ, и параллельный план падал `could not resize
shared memory segment`: нашлось на живом инциденте, когда сессия 50 проверяла
журнал технологических событий двумя тяжёлыми запросами и Postgres выбрал план
на 3 участника. Считать надо не от `shared_buffers` — он лежит в анонимном
mmap (`SHOW shared_memory_type` = `mmap`), `/dev/shm` не трогает. Расходует
`/dev/shm` `dynamic_shared_memory_type = posix` — общая память параллельных
воркеров, и её бюджет parallel hash join — `work_mem × hash_mem_multiplier`
на каждого участника, включая лидера: 64 МБ × 2 (умолчание с PG15) = 128 МБ
на участника; при `max_parallel_workers` = 8 и `per_gather` = 2 это до 4
gather-узлов разом, 12 участников × 128 МБ = 1536 МБ на один hash-узел плана —
1 ГиБ здесь не жёсткий предел, а оценка с запасом против самого инцидента
(3 участника × 128 МБ = 384 МБ против прежних 64 МБ). Проверка на стенде:
`docker exec moskollektor-db-1 df -h /dev/shm` — 1.0G вместо 64M. Разбор
и цифры — `docs/HLD.md` разд. 7.1.

**Стенд достроен 16.09.2026 (MOS-90), к вечеру того же дня контейнеров стало
пять** — `db`, `nginx`, `ml`, `api` и `worker`. Первые четыре `healthy`; проверку
живости для `api` я добавил 16.09.2026, до этого она была у всех служб, кроме той
единственной, ради которой стоит весь стенд — зовёт `python -c` по `/health`, потому
что `curl` в образе бэкенда нет.

**Выкладка с 27.09.2026 — пуш в master, дальше сама.** `/srv/moskollektor` стал
git-копией репозитория: сервер забирает код ключом `/root/.ssh/moskollektor_deploy`,
он заведён на GitHub как deploy key только на чтение. После каждого пуша в master
GitHub Actions (`.github/workflows/deploy.yml`) собирает фронт, гоняет `tsc` и три
самопроверки без базы (`check_schema`, `check_deploy_set`, `check_stale_fetch`),
и если всё зелёное, заходит на сервер своим ключом и запускает
`deploy/deploy.sh`. Ключ Actions стоит в `/root/.ssh/authorized_keys` с
`command="/srv/moskollektor/deploy/deploy.sh",restrict`: чем бы он ни пытался
войти, сервер выполнит только выкладку. Правка одних документов (`docs/**`, `*.md`)
выкладку не запускает. Руками, если Actions лежит:

```
ssh root@135.106.216.101 /srv/moskollektor/deploy/deploy.sh
```

Скрипт берёт вершину `origin/master` и делает всё, что раньше делали руками по
ловушкам ниже: собирает фронт в контейнере `node:26-alpine` (node на сервере нет),
кладёт его в `deploy/nginx/app`, собирает `migrate api worker emulator-smvu`,
накатывает миграции, пересоздаёт nginx, если в compose сменились его тома, и
перезапускает, если менялся `deploy/nginx/`, и ждёт
`healthy` у `api`. Что сейчас на стенде: `curl -sk https://135.106.216.101/version.txt`
отдаёт хеш коммита, а `git -C /srv/moskollektor log -1` на сервере — его же.
Откатывают через `git revert` в master и пуш, а не выкладкой старого коммита мимо git.
`git status` на сервере показывает неотслеживаемые журналы заливки, и так и должно
быть. Собранный фронт лежит в `deploy/nginx/app`, этот каталог стоит в `.gitignore`
и `git reset --hard` его не трогает (задача 1.11, MOS-246). До 27.09.2026 фронт лежал
в `deploy/nginx/html` поверх заглушки, и `git status` показывал там
`M deploy/nginx/html/index.html`. От тех выкладок в `deploy/nginx/html` остались
неотслеживаемые `assets/`, `data/` и `version.txt`: nginx их больше не отдаёт,
их можно удалить командой `git -C /srv/moskollektor clean -fd deploy/nginx/html`.
**Первая выкладка после 1.11 один раз показывает заглушку около минуты:** reset
кладёт её в `html`, а старый контейнер nginx смотрит туда, пока `deploy.sh` не

Ниже — как выкладывали до 27.09.2026 и о какие ловушки спотыкались. Каждая
из них теперь закрыта строкой в `deploy/deploy.sh`.

**Как выкладывать код и что при этом ломается.** Код едет `rsync -a` в
`/srv/moskollektor/backend` и `/srv/moskollektor/db`, потом
`docker compose --profile app build api worker` и `up -d api worker` из
`/srv/moskollektor/deploy`. Собранный интерфейс — `npm run build` на своей машине,
затем `rsync -a --delete frontend/dist/ .../deploy/nginx/html/` (с 27.09.2026 —
`deploy/nginx/app/`, задача 1.11). Две ловушки, на
которых я потерял время 16.09.2026. Первая: `rsync -a` переносит время файла
с машины-источника, поэтому `ls -l` на сервере показывает возраст правки, а не
возраст выкладки — проверять надо содержимым, `docker exec <контейнер> grep -c <новое
слово> <путь>`. Вторая: одиночный файл, смонтированный в контейнер
(`nginx.conf`), привязан по inode, а `rsync` пишет через переименование — после
выкладки `nginx -t` и `nginx -s reload` отрабатывают на СТАРОМ содержимом и молчат
об этом. Помогает `docker compose restart nginx`.

**Третья ловушка, самая дорогая — `code/` в этот список не входил вовсе
(MOS-138, 21.09.2026, нашли 28 и 58).** `backend/Dockerfile` копирует в образ
`api`/`worker` ещё и приёмочные проверки — `.dockerignore` отбирает из `code/`
файлы `check_*.py` и `predictive_metrics.py` (задача 1.13, MOS-120), 13 штук
на 21.09.2026. Но раскладка `code/` на сервер была разовой, под ту же задачу,
и с тех пор его никто не обновлял: следующая пересборка образа запекала то же
старьё, а `docker exec moskollektor-api-1 python code/check_runtime.py`
на приёмке напечатал бы «худший 147: 5,6 с» вместо настоящих 32,7 с — заказчик
получил бы неверное число под видом честного замера.

**Четвёртая ловушка, 22.09.2026: `contracts/` в команде тоже не было.** Слияние
правок ML-команды принесло `contracts/failure.v3.json`, его читает `code/model_failure.py`,
а выложили мы `backend db code` — по этой самой инструкции. `docker build` прошёл
без слова, `contracts` в образ попал вчерашний, и `python code/check_metrics.py --selfcheck`
внутри образа упал `FileNotFoundError: /app/contracts/failure.v3.json`. Пропуск каталога
не роняет сборку никогда: `COPY` берёт то, что лежит на сервере, а лежит там прошлая
выкладка. Теперь каталогов четыре, и что список не разъедется с `COPY` в `backend/Dockerfile`,
проверяет `code/check_deploy_set.py` — он стоит в `delivery/check-all.sh` и краснеет,
если в `Dockerfile` появился пятый `COPY`, а в команде его нет.

**Пятая ловушка, 27.09.2026: новая миграция требует пересобрать и `migrate`.** Миграции
вшиты в образ (`backend/Dockerfile`, `COPY db/migrations`), а у `migrate` свой образ.
`docker compose --profile app build api worker` его не трогает, и `up -d migrate`
отрабатывает старым образом: печатает «готово: 0 новых, 40 уже были», выходит кодом 0
и не накатывает ничего. Так 27.09.2026 чуть не остались ненакатанными 048 и 049 (MOS-36,
MOS-37). Собирать надо `build migrate api worker`, а после выкладки сверять
`SELECT max(filename) FROM public.schema_migration` с последним файлом в `db/migrations/`.

**Правка накатанной миграции стоит одной команды на стенде.** `backend/app/migrate.py:63`
роняет накат, если у накатанного файла сменился `sha256`, — защита от подмены. Значит
правка файла, который на стенде уже стоит, валит следующую выкладку вместе с `api`
и `worker`. 22.09.2026 так вышло с `029_ml_readonly.sql` (задача 1.16): сперва я прогнала
её новый блок самопроверки на живых данных стенда — `DO`, без единой жалобы, то есть
поведение на непустом справочнике не изменилось, — и только потом поправила строку журнала:

```
docker exec moskollektor-db-1 psql -U moskollektor -d moskollektor \
  -c "UPDATE public.schema_migration SET sha256 = '<новый>' WHERE filename = '029_ml_readonly.sql'"
```

Порядок здесь и есть суть: сначала доказать, что новый текст на этих данных делает то же
самое, потом двигать хеш. Наоборот — значит объявить накатанным то, чего никто не проверял.
У заказчика этого шага нет: он ставит с пустого журнала.

**Что едет на стенд для готового образа, поимённо, и откуда:**

```
git archive origin/master backend db code contracts | ssh root@135.106.216.101 \
  "rm -rf /srv/moskollektor/backend /srv/moskollektor/db /srv/moskollektor/code \
   /srv/moskollektor/contracts && tar -x -C /srv/moskollektor"
```

Четыре каталога — `backend/`, `db/`, `code/`, `contracts/`, — и ни один не `rsync`
из рабочего дерева разработчика: в дереве всегда лежит незакоммиченная работа нескольких
сессий одновременно, а образ, который сдаём, обязан отвечать за то, что
закоммичено, а не за то, что оказалось на чьём-то ноутбуке. Правку одного
файла в разработке по-прежнему шлют `rsync` поимённо, как в примерах выше, —
это способ проверить свою правку на живом стенде, а не то, из чего собирают
образ для сдачи. Проверка после раскладки — то же число файлов, что
и в дереве под правила `.dockerignore`:

```
docker exec moskollektor-api-1 sh -c 'ls code/ | wc -l'
git ls-tree -r origin/master --name-only -- code/ | grep -E '^code/(check_.*\.py|predictive_metrics\.py)$' | wc -l
```

## Ручной прогон на стенде: срез задавать всегда

**Ручной прогон без `--as-of` на стенде больше не работает, и это не поломка.**
`backend/app/worker/run.py:167` без флага ставит срезом `datetime.now()`, то есть
сегодняшнюю дату. Выгрузка заказчика кончается 30.06.2026, и на 22.09.2026 срез уходит
от края на 84 суток. Путь модели v3 такой прогон отбивает: `ОШИБКА: ФайлНеГодится: срез
файла 2026-06-30T23:59:59 отстал от среза прогона на 2004.2 ч при допуске 1.5 ч —
ml-score не отработал, считать нечем`, и прогон кончается `failed, стадии 4/6`.
Планировщик при этом работает: он передаёт срез явно, беря его тем же запросом
`app.db.КРАЙ_ДАННЫХ`, которым меряется край. Допуск в 1,5 часа держит
`backend/app/worker/score_v3.py` — файл `score.json` пишет `deploy/ml-score.sh` раз в час,
и прогон обязан считать по свежему файлу, а не по вчерашнему.

**Отсюда правило для ручного прогона: срез задавать всегда.** Проверяете что-то
на стенде —

```
docker exec -w /app moskollektor-worker-1 \
  python -m app.worker.run --as-of 2026-06-30T23:59:59+03:00
```

то есть по краю данных. Хотите увидеть, как экран показывает расхождение среза с краем, —
ставьте срез не дальше чем на час вперёд (`--as-of 2026-07-01T00:59:59+03:00`), дальше
отобьёт та же защита. **Стенд после такого прогона надо вернуть**, иначе дашборд будет
показывать предупреждение до следующего тика: либо прогнать ещё раз с `--as-of` по краю,
либо подождать планировщик — он ходит раз в 4 минуты (`SCHEDULER_INTERVAL_MIN`, свёртка
отдельно раз в 5). Проверить, что вернулось:

```
curl -sk -H "X-User-Login: dispatcher1" https://135.106.216.101/api/data-status
```

Поле `lag_days` обязано стать `0.0`.

## Проигрывание архива: срез идёт по июню вперёд

**Зачем.** Выгрузка кончается 30.06.2026, и на краю данных ничего не происходит: последняя
автозаявка на стенде появилась 22.09.2026, прогон US-17 от 26.09.2026. Проигрывание
заставляет модель считать на срезах 01.06, 02.06 и дальше, и на стенде снова открываются
предупреждения и заводятся заявки. На срезе 01.06 00:00 модель открывает 15 предупреждений
на 32 префиксах; замер 27.09.2026, образ `lgbm-v3-bag-2026.09.21b`.

**Как устроено.** Срез считает `deploy/ml-score.sh`:
архивный момент = `ML_SCORE_REPLAY_FROM` + (сейчас − `ML_SCORE_REPLAY_START`) ×
`ML_SCORE_REPLAY_SPEED`, с точностью до часа и не дальше 30.06 23:59:59. Скорость 24 —
сутки архива за час, при запуске раз в час каждый расчёт сдвигает срез на сутки, и июнь
проходит за 30 часов. Worker при `SCORE_V3_REPLAY=1` берёт срезом меньшее из края
данных и среза в `score.json` (`app.worker.scheduler.срез_проигрывания`). Без этого
выключателя отставший файл по-прежнему роняет прогон защитой «срез файла отстал»:
на живых данных это значит, что ml-score не отработал, и молчать об этом нельзя.

**Включить** — два шага. В `/srv/moskollektor/deploy/.env` дописать
`SCORE_V3_REPLAY=1` и пересоздать worker
(`docker compose --profile app up -d worker`), затем переменные в строку crontab root:

```
7 * * * * ML_SCORE_REPLAY_FROM="2026-06-01 00:00:00" ML_SCORE_REPLAY_START="2026-09-27 10:00:00 UTC" ML_SCORE_REPLAY_SPEED=24 /srv/moskollektor/deploy/ml-score.sh
```

`ML_SCORE_REPLAY_START` — реальный момент начала, по часам хоста; `ML_SCORE_REPLAY_FROM` —
архивный момент, московский. Дошёл до края — срез стоит на 30.06, пока не поменяют START.

**Выключить** — убрать три переменные из строки crontab и `SCORE_V3_REPLAY` из `.env`,
пересоздать worker. Срез вернётся на 30.06 со следующим расчётом, `lag_days` снова
станет `0.0`.

**Что видно на экране, пока идёт проигрывание.** Плитка «данные» на дашборде показывает
разрыв среза с краем выгрузки, в начале около 29 суток. Графики показаний в карточке
объекта тянутся до 30.06, то есть дальше среза. Прогнозы ложатся внутрь проверочного
окна апрель–июнь, и `code/check_metrics.py` получает по ним выдачу модели.

## fail2ban: баним перебор ключей по ssh

Поставила 15.09.2026, пакет `fail2ban` из репозитория Ubuntu, версия 1.0.2.
Повод простой: за сутки до установки в журнале лежало 702 строки неудачных входов,
это чужие сканеры перебирают имена вроде `admin` и `root`. Пароль на вход отключён,
подобрать они ничего не могут, но журнал засоряют и нагрузку дают.

Параметры я положила в `/etc/fail2ban/jail.local` — этот файл перекрывает `jail.conf`
и переживает обновление пакета. Бан на час, пять попыток за десять минут,
`ignoreip = 127.0.0.1/8 ::1`. Час, а не «навсегда», выбран нарочно: если кто-то из нас
упрётся в бан по своей ошибке, он снимется сам, без похода в консоль хостера.

**Одна строка в этом файле обязательна, без неё fail2ban работает вхолостую.**
Фильтр `/etc/fail2ban/filter.d/sshd.conf` ищет в журнале записи юнита `sshd.service`,
а в Ubuntu 24.04 юнит называется `ssh.service`. Разница видна сразу:

```
journalctl _SYSTEMD_UNIT=ssh.service  --since '24 hours ago' | wc -l   # 890
journalctl _SYSTEMD_UNIT=sshd.service --since '24 hours ago' | wc -l   # 1
```

Пока я не дописала в секцию `[sshd]` строку

```
journalmatch = _SYSTEMD_UNIT=ssh.service + _COMM=sshd
```

`fail2ban-client status sshd` показывал живой jail и `Total failed: 0` при семистах
неудачных входах в сутки. То есть служба выглядела рабочей и не ловила ничего.

Проверила двумя способами. Первый — прогнала фильтр по настоящему журналу:

```
fail2ban-regex systemd-journal /etc/fail2ban/filter.d/sshd.conf \
  --journalmatch "_SYSTEMD_UNIT=ssh.service + _COMM=sshd"
```

Он ответил `Failregex: 788 total`, `Lines: 922 lines, 483 ignored, 305 matched`.
Второй — сделала шесть заведомо неудачных входов несуществующим пользователем
с самого сервера на его же адрес. `Total failed` стал 12, `Total banned` — 1,
в списке забаненных появился `135.106.216.101`, а в nftables — правило
`tcp dport 22 ip saddr @addr-set-sshd reject with icmp port-unreachable`.
Тестовый бан я сняла сразу: `fail2ban-client set sshd unbanip 135.106.216.101`.

Служба поднимается после перезагрузки: `systemctl is-enabled fail2ban` отвечает
`enabled`. Места заняла 11 МБ.

**Чего fail2ban у нас не закрывает.** Он вешает правило на входящий трафик к самому
серверу, а докер пускает трафик к опубликованным портам контейнеров мимо этой цепочки.
Значит порты, которые мы откроем наружу для API и карты, fail2ban не защитит — когда
дойдём до публикации стенда, защиту от перебора надо будет ставить отдельно,
на уровне nginx.

## Защита опубликованных портов и базы (задача 1.6, MOS-82)

Четыре замечания независимой приёмки 1.1 закрыты так.

- **nginx слушает оба вида адресов:** `listen [::]:80` и `listen [::]:443 ssl`
  в `deploy/nginx/nginx.conf` (15.09.2026).
- **Перебор к портам 80 и 443 режет nginx, а не fail2ban:** `limit_req_zone`,
  30 запросов в секунду со всплеском до 120 к `/api/`, отказ кодом 429 (15.09.2026;
  27.09.2026 всплеск поднят с 60 до 120 и снят со статики по нагрузочному прогону
  задачи 1.4 — 20 диспетчеров, открывших экран разом, получали 108 отказов;
  разбор в самом `nginx.conf` и в `docs/load-test.md`).
- **Внутри контейнера `db` нет входа без пароля по адресу** (27.09.2026). Правила
  доступа лежат в `deploy/db/pg_hba.conf` и подключаются строкой `hba_file`
  в `deploy/docker-compose.yml`: по сокету без пароля, по любому адресу, включая
  `127.0.0.1`, — `scram-sha-256`. Файл от `initdb` в томе `pgdata` остаётся лежать,
  но база его больше не читает.
- **Заглушка пароля не работает** (27.09.2026). В `deploy/.env.example`
  `POSTGRES_PASSWORD` и `AUTH_SECRET` пустые, а compose с пустым паролем стенд
  не поднимает и называет переменную.

**Что делает первая выкладка после этой правки.** `deploy/deploy.sh` зовёт
`docker compose up -d --wait db`, и compose пересоздаёт контейнер базы, потому что
у него сменились команда и тома. База недоступна несколько секунд, том `pgdata`
не трогается, пул `asyncpg` у `api` переподключается сам (проверено 23.09.2026
на MOS-222). **Проверка на стенде** — с мака, через тот же ssh, что у строки
«лицензии: сборка»:

```
DOCKER_HOST=ssh://root@135.106.216.101 DB_CONTAINER=moskollektor-db-1 API_CONTAINER=moskollektor-api-1 sh deploy/check-db-access.sh
```

Ждём `OK 127.0.0.1 в контейнере: неверный пароль отклонён`, `OK пароль базы
в контейнере: знаков 32, не заглушка` и `OK … верный пароль пускает`. Строка про
`::1` на стенде должна быть `OK`: там в контейнере есть IPv6, а в облачной
песочнице, где проверку писали, его нет, и там она печатает `ПРОПУСК`.

**`AUTH_SECRET` проверяет та же команда:** с `API_CONTAINER` она печатает
`OK AUTH_SECRET в контейнере: знаков 64, не заглушка`. Если в `deploy/.env`
стенда осталась заглушка `СМЕНИ-МЕНЯ`, куки входа подпишет любой, кто читал git:
заменить на `openssl rand -hex 32` и пересоздать `api` (`docker compose up -d api`),
все сессии при этом разлогинятся.

## Резервные копии на стенде (задачи 1.2, 1.9, 1.18)

С 27.09.2026 в составе стенда новый контейнер `backup`: `moskollektor-backup-1`,
образ `postgis/postgis:18-3.6`, без профиля `app`, без портов. Первая выкладка
после этой правки пересоздаёт `db` — у него появились `archive_mode` и
`archive_command`, а `archive_mode` меняется только перезапуском сервера — и
поднимает `backup` строкой `docker compose up -d --wait db backup`
в `deploy/deploy.sh`. Первую копию `backup` снимет в ближайшие 02:00; не ждать
до ночи — `docker compose exec backup sh /backup.sh`. Устройство, учения и
восстановление — `docs/restore.md`.

**Копии на стенде выключены до второго диска.** Место замерено 28.09.2026:
`/dev/sda1` 119 ГБ, занято 81 ГБ, свободно 33 ГБ, докер живёт на корневом разделе.
Учения просят 61 ГБ, демо 55 ГБ, и туда не помещается ни то, ни другое. Код копий
выложен и настроен, но работает вхолостую: в `deploy/.env` стенда стоит
`BACKUP_ENABLED=0`. **Эту строку вписать до вливания ветки:** без неё умолчание —
1, и первая же ночь положит копию на корневой раздел. Разбор — `docs/restore.md`,
разделы «Включить и выключить копии», «Место на диске» и «Сколько хранить».

```
ssh root@135.106.216.101 'printf "\nBACKUP_ENABLED=0\n" >> /srv/moskollektor/deploy/.env'
```

После выкладки проверка отвечает `ВЫКЛ`, а контейнер `backup` пишет, почему молчит:

```
DOCKER_HOST=ssh://root@135.106.216.101 DB_CONTAINER=moskollektor-db-1 sh deploy/check-backup.sh
ssh root@135.106.216.101 'cd /srv/moskollektor/deploy && docker compose logs --tail 1 backup'
```

**Когда будет второй диск** (от 80 ГБ, смонтирован, например, в `/mnt/disk2`),
в `deploy/.env` стенда вписать `BACKUP_DIR=/mnt/disk2/backups` и
`BACKUP_ENABLED=1`, затем `sh deploy.sh`. Дальше команды с мака:

```
DOCKER_HOST=ssh://root@135.106.216.101 DB_CONTAINER=moskollektor-db-1 sh deploy/check-backup.sh
DOCKER_HOST=ssh://root@135.106.216.101 DB_CONTAINER=moskollektor-db-1 sh deploy/wal-rate.sh 60
ssh root@135.106.216.101 'cd /srv/moskollektor/deploy && docker compose --profile app stop worker emulator-smvu && docker compose exec -T backup sh /backup.sh --drill; docker compose --profile app start worker emulator-smvu'
```

Первая — сразу: архив журнала идёт. Про журнал копий она будет красной до первой
ночной копии, так и должно быть. Не ждать до ночи —
`docker compose exec backup sh /backup.sh`.

Вторая — через сутки, когда есть ночная копия, и не в 02:00. Она считает, сколько
журнала стенд пишет за сутки, и печатает, сколько копий помещается на второй диск.
Если напечатанное `BACKUP_KEEP` меньше, чем в `deploy/.env`, ставим напечатанное.

Третья — учения. Они разворачиваются в `/mnt/disk2/backups/drill`, рядом с копиями.
Команда останавливает `worker` и `emulator-smvu`, иначе сверка разойдётся на
строках, записанных по ходу, и запускает их обратно, даже если учения упали
(`;`, а не `&&`). Время в секундах ляжет строкой в журнал копий, это и есть замер
НФ-39.
