# Протокол нагрузочных замеров

Здесь лежат замеры, которыми мы закрываем нормативы времени из постановки и ТЗ.
Каждый замер называет стенд, объём данных и дату: число без этих трёх вещей
на приёмке ничего не доказывает.

Стенд один и тот же — `135.106.216.101`, Ubuntu 24.04.4, 11 ГБ оперативной памяти,
PostgreSQL 18.6 в контейнере `moskollektor-db-1`, `shared_buffers` 3 ГБ,
`work_mem` 64 МБ. Заказчик будет мерить на своём железе, и наши числа — это нижняя
граница запаса, а не обещание.

## Расчёт прогноза

Закрывает строку приёмки **М-21** (время формирования прогноза меньше 5 минут
на продуктивном объёме) и **НФ-72** (инференс по одному объекту меньше 5 минут).
Задачи `Q3.5` (`MOS-35`) и `Q3.8` (`MOS-99`).

### Три прогона, 17.09.2026

Команда:

```
docker exec moskollektor-api-1 python -m app.worker.run --as-of 2026-06-30T23:59:59+03:00
```

Времена стадий взяты из `pred.run`, а не из секундомера в голове: расчёт пишет
их сам, шестью колонками `ms_*`.

| Прогон | Граница данных | Свёртка | Признаки | Инференс | Объяснения | Запись | **Итого** |
|---|---|---|---|---|---|---|---|
| 55 | 4 831 | 3 005 | 24 099 | 59 | 74 | 472 | **32 540** |
| 56 | 4 609 | 3 094 | 24 402 | 66 | 73 | 463 | **32 707** |
| 57 | 4 763 | 2 988 | 24 307 | 59 | 76 | 446 | **32 639** |

Все числа в миллисекундах, по 3 173 участкам каждый.

**Итог — это сумма шести стадий, а не время жизни процесса.** Если мерить
`finished_at` минус `started_at` из той же таблицы, выходит на десятую больше:
32,6 / 32,8 / 32,7 секунды. Разницу дают стадия автозаявок, у которой нет своей
колонки `ms_*`, и запись итога в журнал. Обе величины верны, но на приёмке надо
называть, какую именно показываешь, иначе два человека посчитают по-разному
и решат, что кто-то ошибся. Мы показываем сумму стадий: она раскладывается
на слагаемые, а разность двух отметок времени — нет.

**Худший прогон — 56, это 32,7 секунды при нормативе 300.** Запас девятикратный.

**Инференс занимает 66 миллисекунд из 32 707.** Это 0,2 % расчёта. Оптимизировать
модель бессмысленно: она не тратит времени. Всё время уходит на чтение.

### НФ-72: расчёт по одному объекту

```
docker exec moskollektor-api-1 python -m app.worker.run --as-of 2026-06-30T23:59:59+03:00 --limit 1
```

Прогон 58, один участок: **12,8 секунды** при нормативе 300.

Времени уходит почти столько же, сколько на весь парк, и это не ошибка замера.
Постоянная часть расчёта от числа объектов не зависит: граница данных — это один
`max(read_time)` по журналу, суточная свёртка обновляется за двое суток по всему
парку, а не по одному участку. На один объект приходится только сборка его
признаков.

### Что мы сделали, чтобы получить эти числа

До правки 17.09.2026 расчёт занимал 56,4 секунды, из них 48,5 — сборка признаков.
Профиль по запросам внутри стадии (его печатает диагностика, ключ `мс_запросов`):

| Запрос | Было, мс | Стало, мс |
|---|---|---|
| Интервалы между записями канала | 22 435 | 19 050 |
| Счётчики и фоны по каналу | 25 668 | 4 192 |
| Освежить суточную свёртку по каналу | — | 768 |
| Последняя запись участка без окна | 258 | 173 |
| Покрытие свёртки | 70 | 45 |
| Девять признаков по участку | 58 | 67 |
| Остальные четыре запроса | 43 | 19 |
| **Стадия целиком** | **48 532** | **24 314** |

**Первое: суточная свёртка по каналу** (`feat.channel_daily`, миграция
`db/migrations/022_channel_daily.sql`). Счётчики по каналу за 7 суток, 8 недель
и год читали журнал — 60 096 602 строки. Теперь они читают свёртку — 652 384
строки, в девяносто два раза меньше. Запрос стал быстрее в 6,1 раза.

Заполняет свёртку сама стадия сборки признаков, перед тем как её прочитать:
`освежить_канальную_свёртку()` в `backend/app/worker/features.py`. Первый прогон
после миграции догоняет год целиком — на стенде это 41 секунда и 662 596 строк,
один раз; дальше хватает двух суток и 768 миллисекунд.

**Второе: одна группировка вместо двух** в запросе интервалов. Он группировал
4,6 млн строк по каналу, а потом соединял результат обратно с тем же CTE
и группировал второй раз — только чтобы сосчитать интервалы длиннее 95-го
перцентиля. Теперь недельные интервалы канала едут из первой же группировки
массивом. Выигрыш 3,4 секунды, 15 %.

### Проверка, что ускорение не поменяло ни одного числа

Быстрее — это не результат, если признаки при этом поехали. Заглушка модели
отвечает константой и проглотит любой вход, поэтому «прогнозов записано столько же»
ничего не доказывает.

Я снял вектор признаков по всем участкам до правки и после и сравнил попарно:

```
сравнено клеток 69806 = 3173 участков × 22 признаков
расхождений 0; участков только в ДО 0, только в ПОСЛЕ 0
ИТОГ: снимки совпали полностью
```

Сверок было две — отдельно после суточной свёртки и отдельно после правки
интервалов, и обе дали ноль расхождений.

**Почему совпало точно, а не «почти».** Окна признаков считаются от МОМЕНТА среза,
а свёртка сложена по суткам, и границы окон почти никогда не приходятся на полночь.
При срезе 30.06.2026 23:59:59 недельное окно начинается 23.06 в 23:59:59 — сутки
23.06 попадают в окно одной последней секундой. Округлить их в любую сторону значит
соврать. Поэтому запрос сложен из двух частей: из свёртки берутся целые сутки,
а пять граничных суток читаются из журнала с теми же условиями по времени, что
стояли в прежнем запросе. Граничных суток пять: начала недельного, месячного,
восьминедельного и годового окон плюс сами сутки среза.

### Чего мы не стали делать

**Не трогали настройки сервера.** Сортировка в запросе интервалов уходила на диск —
`external merge Disk: 183 888 kB`. Я поднял `work_mem` с 64 МБ до 512 МБ в сеансе:
сортировка стала `quicksort Memory: 395 762 kB`, а время не изменилось вовсе,
15,77 секунды против 15,81. Значит дело не в сортировке, и менять настройку базы
незачем.

**Не строили индекс `(channel_id, read_time, journal_id)` на `smvu.reading`.**
Он убрал бы сортировку в запросе интервалов, но это индекс по 313 млн строк —
часы построения и десятки гигабайт на диске ради 19 секунд при нормативе 300.
Упрёмся на железе заказчика — вернёмся.

### Как повторить замер

```
# один прогон с профилем по стадиям
docker exec moskollektor-api-1 python -m app.worker.run --as-of 2026-06-30T23:59:59+03:00

# профиль по запросам внутри стадии признаков и снимок вектора
docker exec moskollektor-api-1 python /tmp/snapshot_features.py /tmp/snap.json 2026-06-30T23:59:59+03:00

# времена стадий из журнала прогонов
SELECT run_id, ms_fetch, ms_aggregate, ms_features, ms_inference, ms_explain, ms_write
  FROM pred.run ORDER BY run_id DESC LIMIT 3;
```
